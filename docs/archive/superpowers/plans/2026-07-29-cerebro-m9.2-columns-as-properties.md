# Cerebro M9.2 — Columns Are Properties

> **Status: DRAFT.** Milestone-altitude plan. Ships with M9.1 — both rewrite `Presentation`.

**Goal:** A view's columns are the source type's properties, editable from the view. Adding a column adds a property to the type; reordering and resizing persist to the view.

**Why:** In Notion, the table header is the database schema. In cerebro today the header is a read-only projection of a field list that is sometimes the wrong type's, and the only way to add a property is the Type screen's Properties tab.

---

## Current state

**`ProjectPage` hardcodes the type.** [ProjectPage.tsx:154-157](../../../src/pages/ProjectPage.tsx#L154-L157) resolves `schema.types.get('Work item')?.fields` and passes it to every layout, regardless of what is on the canvas. The comment is honest about it — the project canvas *was* Work-item-only — but the same page now renders scoped saved views.

**Typeless views have no columns at all.** [CollectionPage.tsx:56-62](../../../src/pages/CollectionPage.tsx#L56-L62) resolves `fields` to `[]` when `source.type === null`, and [ViewToolbar.tsx:131](../../../src/views/ViewToolbar.tsx#L131) hides `PropertyVisibility` when `fields === undefined`… but `[]` is not `undefined`, so the picker renders empty rather than hiding. Either way an "Everything" view is uncolumnable.

**Nothing creates a property from a view.** `addFieldToType` exists in [app/typeActions.ts](../../../src/app/typeActions.ts) and is wired only to [TypePage](../../../src/pages/TypePage.tsx)'s `AddPropertyPanel`.

**Columns cannot be reordered or resized.** `visibleFields: string[]` carries order but [PropertyVisibility](../../../src/views/PropertyVisibility.tsx) only toggles membership, and width is the module constant `COL_W = 150` in both [TableView.tsx](../../../src/views/TableView.tsx) and [TreeView.tsx:12](../../../src/views/TreeView.tsx#L12).

## Column universe

Replace all three ad-hoc resolutions with one engine function:

```ts
// engine/columns.ts
export function columnUniverse(
  source: ViewSource,
  entries: Entry[],
  schema: Schema,
): FieldDef[]
```

- `source.type !== null` → that type's declared fields.
- `source.type === null` → the union of declared fields across every type present in the selected entries, plus undeclared frontmatter keys observed on those entries (kind `text`), deduped by name. A mixed view gets the columns its records actually have.

Field name collisions across types with different kinds resolve to the first declared kind and mark the column `heterogeneous: true`; the header shows the kind icon with a muted qualifier and cells fall back to read-only display where the kind does not match the record's own declaration. This is the same rule [TreeView.tsx:52-65](../../../src/views/TreeView.tsx#L52-L65) already applies to child rows of a foreign type — generalize that, do not reinvent it.

`ProjectPage` calls `columnUniverse({type: 'Work item', project: path}, …)` for the Items tab and the active view's own source for view tabs. The hardcode goes away.

## Add a property from the header

A trailing `+` cell in the table header, and a "+ New property" row at the bottom of the `PropertyVisibility` popover for the non-table layouts.

Flow: pick name and kind (reuse [AddPropertyPanel](../../../src/detail/AddPropertyPanel.tsx) verbatim) → `addFieldToType(sourceType, name, kind)` writes the Type doc → `rescan()` → append `{field: name}` to `presentation.columns` → persist the view.

**Guards:**
- Disabled with an explanatory tooltip when `source.type === null` — an "Everything" view has no single type to add a property to. This is the honest failure; silently picking one type would corrupt the schema.
- Disabled for locked built-ins per [isLockedField](../../../src/engine/typeCatalog.ts) — same rule the Type screen enforces.
- The write is to the *type*, not the view: every other view over that type gains the property (hidden by default there, since only this view appends it to `columns`).

## Reorder and resize

**Reorder** — drag a header cell. `columns` is an ordered array so this is a splice plus persist. Also add explicit "Move left / Move right" items to the per-column header menu; drag alone is not reachable by keyboard.

**Resize** — drag the header cell's right border. Writes `ColumnSpec.width`. Persisted per view, so the same type looks different in two views, which is correct. Minimum 60px; double-click the divider resets to auto (clears `width`).

**Hide** — `ColumnSpec.hidden` rather than removal from the array, so re-showing a column returns it to its position instead of appending it. `PropertyVisibility` toggles `hidden`.

**Per-column header menu** consolidates: sort asc/desc (prepends to `sort`), group by this (prepends to `group`), hide, move, edit property (opens the Type screen's field editor inline), delete property (confirms, then `removeFieldFromType`).

## Sizing contract

`COL_W` stays as the default. `TableView` and `TreeView` both read `ColumnSpec.width ?? COL_W`. `TreeView`'s `totalWidth` computation ([TreeView.tsx:139](../../../src/views/TreeView.tsx#L139)) becomes a sum rather than a multiply.

## Acceptance criteria

1. Opening the "At risk" view and adding a `Blocked by` relation column creates the property on the `Work item` type doc and shows it in that view only.
2. A view with `source.type: null` shows the union of its records' properties as columns.
3. Dragging a column changes its position and the change survives reload.
4. Resizing persists per view; the same type in another view keeps its own widths.
5. Hiding then re-showing a column returns it to its original position.
6. The project canvas shows the correct type's properties when a scoped view tab is active.
7. `+` is disabled with a tooltip on typeless views.
