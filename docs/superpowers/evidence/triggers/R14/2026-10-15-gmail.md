# Gmail evidence pack — pending owner acceptance

This pack asks for two local page kinds in one vault store: a `thread` page of
mail headers, and `thread_text` for message text the person explicitly asks to
keep during an attended conversation. The gate is closed. This document is a
draft, not an acceptance or a claim that a live account has been tested.

The consumer is the person reviewing correspondence on their own records.
The workflow is: ask the assistant to read recent threads with the person's
Gmail connector, keep bounded header digests, inspect Correspondence, and ask
for an individual message's text only when needed. There is no sync daemon,
sending, or in-app OAuth. No token enters Cerebro; the person's own Claude Code
connector performs authentication. Run grants and connector status retain
M54.9's and M54.11's boundaries.

Today's EMAIL-0 primitive cannot offer reliable correspondence: a model's
narrative recap is not a bounded, repeatable header record, and storing mail as
a web source would send private addresses and message text into tracked files.
The planned writer builds these pages from the fetch result, uses the source
identity rules to update the same page, and refuses a mail URL as a web cache.

## Privacy, storage, retention and health

`thread` keeps bounded header facts and addresses under `sources/mail/`.
It never keeps bcc, mailbox labels or message bodies. The folder and its
`.comments/` sidecars stay out of git, including files tracked by an older
checkpoint. Untracking does not erase old commits. Only an attended Cerebro
conversation may read these local pages; background runs and token clients
may not. The owner chooses when to prune them.

`thread_text` keeps only requested message text in its own page under that
same ignored folder. It is never fetched or written by a background sweep.
The body is bounded, stripped to the reply and inert; it may still contain
personal information. Deletion uses the vault's Trash and its retention rules.

Closed, wrong-scope or unlisted-kind gates refuse writes with a clear reason.
Unavailable reads stay unavailable, never an empty inbox. A repeat fetch
updates the same identity. Truncation and skipped messages are counted. The
cost is the person's own CLI/connector usage plus local parsing; no cost
estimate is invented for unmetered calls.
