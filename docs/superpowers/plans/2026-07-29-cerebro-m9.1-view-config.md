# Cerebro M9.1 — View Configuration v2

> **Status: DRAFT.** Milestone-altitude plan. Expand to task contracts before execution.

**Goal:** A saved view can express nested grouping, a multi-level record hierarchy, and multi-key sorting — configured from the toolbar, persisted to YAML, with UI state that survives navigation.

**Why:** The current `Presentation` allows exactly one grouping level, one sort key, and one hierarchy relation applied uniformly at every depth. "The OKR nesting doesn't stick" is three separate defects in that model, not a bug in the tree view.

---

## The three defects behind "OKR nesting doesn't stick"

1. **The toolbar cannot reach the tree layout.** [ViewToolbar.tsx:91-105](../../../src/views/ViewToolbar.tsx#L91-L105) offers `split | table | list | board`. The OKR view's `type: tree` matches no segment, so nothing reads as selected — and clicking any segment persists you out of tree, recoverable only through the settings dialog. `childrenVia` survives the object spreads, so the config is intact; it is simply unreachable.

2. **One hierarchy spec, applied at every depth.** [relations.ts:40-58](../../../src/engine/relations.ts#L40-L58) takes a single `ChildrenSpec` and `TreeView` re-applies it per level ([TreeView.tsx:120-137](../../../src/views/TreeView.tsx#L120-L137)). Objective → Key result works. Key result → Work item can never render, because the descent from depth 1 uses the same `{type: 'Key result', field: 'objective'}` spec that produced depth 1.

3. **Grouping and nesting are separate axes.** `groupBy: string | null` ([types.ts:109](../../../src/engine/types.ts#L109)) is read by list/board/table; `childrenVia` is read only by tree. Notion has one concept — an ordered chain — and a hierarchy is a relational grouping chain. Two axes means the tree layout cannot group and the table layout cannot nest.

Plus: collapse state is `useState` in [TreeView.tsx:104](../../../src/views/TreeView.tsx#L104) and TableView, so every expansion resets on navigation.

## Target model

```ts
export interface GroupSpec {
  field: string;
  dir?: 'asc' | 'desc';        // order of the groups themselves; default declared order
  hideEmpty?: boolean;          // default false — boards need empty columns
}

export interface SortSpec {
  field: string;
  dir: 'asc' | 'desc';
}

export interface ColumnSpec {
  field: string;
  width?: number;               // px; undefined = COL_W default
  hidden?: boolean;             // present-but-off, so toggling preserves position
  wrap?: boolean;
}

export interface Presentation {
  type: 'list' | 'board' | 'split' | 'table' | 'tree' | 'calendar';
  group: GroupSpec[];           // ordered: primary, secondary, …
  sort: SortSpec[];             // ordered multi-key
  columns: ColumnSpec[];
  hierarchy: ChildrenSpec[];    // ordered descent chain, one spec per depth
  rowHeight?: 'compact' | 'default' | 'tall';
}
```

`'calendar'` is added to the union in M9.1 so M10 does not re-migrate the type; no calendar view is built here. `ChildrenSpec` is unchanged.

### Back-compatible parsing

`parsePresentation` accepts both shapes and always writes the new one:

| Legacy key | Reads into | Rule |
|---|---|---|
| `groupBy: 'status'` | `group: [{field: 'status'}]` | `null` → `[]` |
| `orderBy: {field, dir}` | `sort: [{field, dir}]` | always length 1 |
| `visibleFields: string[]` | `columns: [{field}, …]` | order preserved |
| `childrenVia: spec` | `hierarchy: [spec]` | `null` → `[]` |

When both a legacy key and its v2 counterpart are present, **v2 wins** — a file mid-migration should not have its new config silently overridden by a stale key. `serializeView` emits v2 keys only.

The tolerant-parse contract holds: a malformed `group` entry is dropped, not fatal. A `hierarchy` array longer than `MAX_DEPTH` (6) is truncated at parse.

## Engine changes

**`engine/grouping.ts` — `groupTree(entries, specs, schema): GroupNode[]`.** Recursive. Current `groupEntries` becomes the depth-0 case and stays exported for the single-level callers until they migrate.

```ts
export interface GroupNode extends Group {
  depth: number;
  children: GroupNode[];   // empty at the last spec level
  // `entries` is populated only on leaf nodes; interior nodes carry counts
  count: number;           // recursive total, so a collapsed parent still reports truth
}
```

Ghost groups, the trailing `__none__` bucket, and declared-option ordering all recurse unchanged — the existing rules in [grouping.ts:9-15](../../../src/engine/grouping.ts#L9-L15) apply per level.

**`engine/collections.ts` — `sortEntries` takes `SortSpec[]`.** Comparator chain: first non-zero wins. The existing per-field rules (declared option order, numeric, ISO-string, empty-last) move into a `compareBy(field)` helper the chain calls. Empty-last must be evaluated **per key**, not globally, or a record missing the primary sort field never reaches the secondary comparison.

**`engine/relations.ts` — `childrenOf` takes the depth.** New signature: `childrenAt(entry, hierarchy, depth, entries, index)` returns `[]` when `depth >= hierarchy.length`. `childrenOf` stays for single-spec callers. The relation index is unchanged — it is keyed by target path and field name, which already supports heterogeneous descent.

**Cycle guard survives.** `TreeView`'s `seen` set is per-branch and still needed: `hierarchy: [{Objective→KR}, {KR→Objective}]` is expressible and would loop.

## UI changes

**`ViewToolbar` gains the Hierarchy segment** and, when `type === 'tree'`, a hierarchy chain editor. The layout switcher becomes `split | table | list | board | tree`, with `tree` labelled "Hierarchy".

**Group control becomes a popover, not a `Dropdown`.** A single-select cannot express an ordered chain. New `GroupBuilder` component, modelled on the existing [FilterBuilder](../../../src/views/FilterBuilder.tsx): a list of rows, each a field select plus a remove button, with "+ Add sub-group". Cap at 3 levels — beyond that the visual nesting stops being legible, and Notion caps at 3 for the same reason.

**Sort control likewise becomes a chain builder.** Same shape; no hard cap needed.

**Hierarchy chain editor** reuses the option-building logic already in [ViewSettingsDialog.tsx:66-76](../../../src/app/ViewSettingsDialog.tsx#L66-L76) — forward relations from the source type, reverse relations from any type pointing back at it. Level *n+1*'s options derive from level *n*'s resulting type, which is the whole point: after `Objective → Key result`, the next dropdown offers relations on **Key result**, so `Key result → Work item` becomes selectable. Extract that logic into `engine/hierarchyOptions.ts` so the dialog and the toolbar share one implementation.

**Layout support matrix** — what each layout reads:

| Layout | `group` | `sort` | `columns` | `hierarchy` |
|---|---|---|---|---|
| table | all levels, as nested header rows | all | yes | yes — nests within a group |
| list | all levels, as nested section headers | all | as chips | no |
| board | `group[0]` = columns, `group[1]` = swimlanes | all | as chips | no |
| tree | `group[0]` only, above the roots | all | yes | all levels |
| split | — | all | — | — |

Board sub-grouping as swimlanes is Notion's model and falls out of `groupTree` for free.

**Collapse state moves to `uiStore`.** `collapsedGroups: Record<string, Record<string, boolean>>` — outer key is the view id (or `project:<path>` / `type:<name>` for the unsaved surfaces), inner key is the existing composite group/row key. Add `toggleCollapsed(scope, key)` and `isCollapsed(scope, key)`. This is deliberately not persisted to disk in M9.1; it survives navigation within a session, which is the actual complaint.

## Acceptance criteria

1. `demo-vault/views/okr-tree.yml` extended to `hierarchy: [{Objective→Key result}, {Key result→Work item}]` renders three levels.
2. Switching the OKR view to Table and back to Hierarchy from the toolbar preserves the hierarchy chain.
3. Expanding rows, navigating to another view, and returning preserves the expansion.
4. A table grouped by `status` then `assignee` renders nested headers with correct recursive counts.
5. A board grouped by `status` then `assignee` renders assignee swimlanes.
6. Sorting by `priority` then `due` orders correctly, including records missing `priority`.
7. Every M8-era view file in `demo-vault/views/` opens unchanged; after any toolbar edit the file is rewritten in v2 keys.
8. `engine/views.test.ts` gains round-trip cases for both shapes; `grouping.test.ts` gains nesting cases.
