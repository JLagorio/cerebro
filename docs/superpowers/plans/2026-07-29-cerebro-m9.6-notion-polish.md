# Cerebro M9.6 — Notion Polish

> **Status: DRAFT.** Depends on M9.1 + M9.2. The smallest milestone and the one that decides whether the rest feels finished.

**Goal:** Types and files carry their identity consistently everywhere, records are creatable and editable from every surface that lists them, and the keyboard reaches the things the mouse can.

**Why:** The engine is close to Notion's model — a type is a database, a view is a saved query, properties are typed and configurable. What is missing is the thousand small consistencies that make it *feel* like one system rather than a set of screens over a shared store.

---

## 1. Type identity is consistent

`typeStyle(type, schema)` in [typeCatalog.ts](../../../src/engine/typeCatalog.ts) resolves icon and color, and is used in [TreeView](../../../src/views/TreeView.tsx#L170), [ProjectPage](../../../src/pages/ProjectPage.tsx#L219), and [ListView](../../../src/views/ListView.tsx#L128). It is *not* used consistently in the detail panel, quick-open results, the file tree, board cards, or agent action cards — several of which hardcode `file-text`.

Audit every place a record is rendered and route through `typeStyle`. A `Risk` should look like a Risk in the sidebar, in a table row, in QuickOpen, in a wikilink chip, and in the assistant's transcript.

**Extend it to files.** The [FileTree](../../../src/components/FileTree.tsx) shows generic file icons. A `.md` with `type: Meeting` should show the Meeting icon there too — the file tree is a view of the same records.

## 2. Create from everywhere

Notion's rule: any surface that lists records can create one.

- **Table** — a trailing `+ New` row, inheriting the active group's value the way [QuickAddRow](../../../src/views/ListView.tsx#L20) already does for lists. Extract that logic; it currently only exists inside ListView and only when `project !== null`.
- **Board** — `+` per column, presetting the column's group value.
- **Hierarchy** — `+ Add child` on a row, creating a record of the child type with the descent relation pre-filled. This is the one that makes the OKR view usable rather than just readable: adding a key result to an objective should not require navigating to the Key result type.
- **Type screen** — a create button; today [TypePage](../../../src/pages/TypePage.tsx) can only list.

All of them write through the existing `createItem` path. The folder decision — project `items/` vs the type's conventional folder — needs one rule in `engine/` rather than per-caller guesses.

## 3. Inline editing parity

[TableView](../../../src/views/TableView.tsx) cells are inline-editable via [FieldEditor](../../../src/detail/FieldEditor.tsx). [ListView](../../../src/views/ListView.tsx#L136) renders read-only [FieldChip](../../../src/views/FieldChip.tsx)s. Board cards likewise.

Make chips editable on click in list and board. Same `FieldEditor`, `compact` variant — TreeView already does exactly this at [TreeView.tsx:90](../../../src/views/TreeView.tsx#L90).

## 4. Empty and error states

`EmptyState` exists ([components/ui/EmptyState.tsx](../../../src/components/ui/EmptyState.tsx)) and is used in one place — [CollectionPage](../../../src/pages/CollectionPage.tsx#L67)'s missing-view case. Everywhere else empties are bare text: [TreeView.tsx:231](../../../src/views/TreeView.tsx#L231) "No records yet.", [TypePage.tsx:247](../../../src/pages/TypePage.tsx#L247) "No properties declared yet."

Every empty gets an `EmptyState` with an action. "No records yet" on a filtered view should offer to clear the filter; on an unfiltered one, to create the first record. An empty that only reports emptiness is the non-functional chrome the product rule prohibits — it occupies the space where the next action belongs.

## 5. Density and keyboard

**Row height** — `rowHeight` lands in `Presentation` in M9.1; wire it. Current heights are hardcoded (`h-10` list, `h-9` tree).

**Keyboard navigation** — arrow keys move the row selection, `Enter` opens the detail panel, `Space` toggles expansion, `Esc` closes. Currently every layout is mouse-only; rows are `<div role="row">` with `onClick` and no `tabIndex`, which is also an accessibility gap, not only an ergonomic one.

**Command palette coverage** — [QuickOpen](../../../src/app/QuickOpen.tsx) finds notes. It should also reach views, types, and actions ("Group by status", "Add property"). Tolaria's `buildGitCommands` pattern ([gitCommands.ts](../../tolaria-main/src/hooks/commands/gitCommands.ts)) — feature modules contributing `CommandAction[]` to a shared registry — is the right shape and worth adopting before the surface grows further.

## 6. Type screen completeness

[TypePage](../../../src/pages/TypePage.tsx)'s Properties tab covers rename, kind, options, statuses, rollup config, and format. Missing:

- **Reorder properties** — `fields` order drives default column order; there is no way to change it.
- **Description per property** — a `description:` on the field def, surfaced as a tooltip in headers and the detail panel.
- **Default values** — `default:` applied on record creation.
- **Templates per type** — [lib/templates.ts](../../../src/lib/templates.ts) has `isTemplate`; the type screen should let you pick which template new records of the type start from.

## Acceptance criteria

1. A `Risk` record shows the same icon and color in every surface that renders it.
2. Every listing layout can create a record, presetting the active group's value.
3. Hierarchy rows offer "Add child" with the descent relation pre-filled.
4. Field chips are editable in list and board.
5. Every empty state offers an action.
6. Arrow keys, Enter, Space, and Esc navigate every layout.
7. QuickOpen finds views, types, and commands.
8. Properties can be reordered on the type screen and the order drives default columns.
