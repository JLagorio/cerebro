## What M25.1 and M25.2 built (do not re-derive)

### M25.1 — `c76f677`

- `src-tauri/src/runtime/schema.rs` — the whole `user_version = 3` DDL as an
  executable contract: closed enums are `CHECK`s, counts are `>= 0`, hashes
  are shape-checked, times are checked for the `…Z` spelling. Two constraints
  are behaviour: an ambient run must name a vault, and a `claimed` item must
  carry a lease.
- `runtime/mod.rs` — migrations are a numbered list, each one `BEGIN
  IMMEDIATE` → DDL → **validation inside the transaction** → version stamp →
  commit. Failure rolls back, names the version, pauses ambient. Corruption is
  quarantined to `runtime.db.corrupt-<stamp>`, never overwritten; an
  `runtime.db.open` marker file distinguishes clean from unclean shutdown
  (`quick_check` vs `integrity_check`). `open_existing()` is the hot-path
  connect that refuses to migrate.
- `runtime/scope.rs` — **`vault_id` is derived from the canonicalized path AND
  recorded** in `vault_registry`. Derived so a deleted database re-derives the
  same ids and rebuilt rows rejoin their vault. Moving a vault folder mints a
  new `vault_id`; that is correct for the local questions it answers, and
  `store_uuid` carries portable identity.
- `runtime/normalize.rs` — the normalized snapshot. **No timestamp is in it,
  by construction**; that is the whole point (a `git checkout` rewrites every
  mtime and changes no content). `NORMALIZER_VERSION = "vault-entry-v1"`.
- `runtime/scheduler.rs` — row storage + the seven states. `put`,
  `counts_by_state`, `keys_in_state`, `get`, `move_state`.
- `runtime/import.rs` — the one-shot upgrade. Imports the three ledgers that
  were actually durable (`cerebro.learnAttempts` / `.skillRuns` /
  `.triggerRuns`) and HOLDS everything it cannot prove as `baseline_held`.
  Consults mtime exactly once, deliberately, in the one place the legacy
  evidence is keyed on it. Rows and the completion marker commit together.
- `runtime/recovery.rs` — the conservative recovery planner.
  `receipts_in_ledger()` is the **M25.3 seam** and returns empty; the planner
  it drives is complete and tested against injected receipts.
- `runtime/status.rs` — process-level `Ready | MigrationFailed | Recovering`.
  Has a `test_lock()` because it is global; any test that asserts on it must
  take the lock or it will pass alone and fail in the suite.

### M25.2 — `7f1dfea`

- `agent/usage.rs` — parses the four disjoint counts off recorded fixtures in
  `src-tauri/fixtures/cli-stream/`. Unknown wire fields → one
  `operational_log` row per run. `KNOWN_UNCOUNTED` is the deliberately-ignored
  list, kept separate so the log does not fill with the same two lines.
- `agent/meter.rs` — the reader thread tallies and writes straight to the
  runtime DB. **Usage never travels on the UI event channel.** Also holds the
  elapsed watchdog.
- `shared/runtime/budget-defaults.v1.json` + `.sha256` — compiled in,
  digest-pinned. Regenerate with
  `cargo test --lib runtime::budget::tests::write_defaults_digest -- --ignored`.
- `runtime/budget.rs` — immutable settings versions (every edit appends, even
  a revert), local-day windows via `chrono-tz` (honest 23/25-hour DST days, a
  skipped midnight starts at the first minute that exists), `budget_days` rows
  that COPY their ceilings, and the gate. **Degradation is one formula**: each
  lane's shed threshold is interpolated from its registry priority (lowest
  sheds at `warning_ppm`, highest at the ceiling), and the refusal names the
  dimension that is filling rather than an opaque "degraded".
- `runtime/dispatch.rs` — `claim()` is gate + reservation + scheduler claim +

  `finalize()` is the second transaction. Missing usage is `unknown`, never
  zero, and pauses ambient. `recover_expired_leases()` is the crash path.
  Kill-point tests cover every boundary.

### M26.3c — DONE (this commit) — **AGENTS CAN NOW MUTATE**

This is the commit the whole milestone was arguing toward, and the one to read
first if something goes wrong. The proposal tools are registered on the live
loopback MCP server, **behind a switch that defaults off**.

Three decisions were the owner's, taken after a written comparison:

1. **One tool per op**, `propose_<op>`, plus terminal `commit_proposals`. The
   prefix also resolves the `cache_source` collision — it is both a
   hand-written write tool and a policy op.
2. **`revert_proposal` is NOT agent-facing**, expressed as `agent_facing:
   false` in the artifact rather than a list in Rust. It is MEDIUM, MEDIUM
   auto-applies, and an agent-facing revert would silently undo an applied
   mutation — including one a human had just approved on a HIGH card, with no
   second card to notice. Every other op is agent-facing; the default is true,
   so the artifact says only where the answer is no.
3. **A real kill switch**: `AppConfig.agent_proposals_enabled`, default false.
   There was none before — `cerebro.autoLearn` is the distiller flag and
   `ambient.global_pause` is M25's ambient pause, and neither gates the
   catalog. **This is what M26.9 flips.** Registration is not activation.

Implementation notes a reviewer will want:

- **The names are GENERATED** from `table.agent_facing_ops()`. There is no
  second inventory — and `tool_policy` (the `--allowedTools` grant in
  `agent/mod.rs`) was a third one, hand-maintained with nothing asserting it
  matched the served catalog. It now derives from `mcp::tool_catalog(true)`
  and `the_grant_is_exactly_the_served_catalog` proves it.
- **The registration gate** (`mcp::registration_gate`) refuses to build ANY
  proposal tool unless `ancestry::table_binding` passes and `create_belief`
  still requires `candidate_receipt_current` and declares its four receipt
  codes. Against the frozen v1 table it refuses by naming the absent binding.
- **`run_id` rides the bearer token** (`mcp::run_id_of`). `commit_proposals`
  refuses members belonging to another run, and that check is only meaningful
  if a caller cannot name a run it does not hold the token for.
- **The receipt is minted server-side** inside the create path; a
  caller-supplied one is refused `candidate_receipt_caller_authored`.
- **`payload` is an open object in the inputSchema** on purpose. A
  hand-written JSON Schema per op would be a second copy of `ProposalOp`'s
  twenty closed variants, free to drift from the frozen union. serde plus
  `ProposalV1::validate` is the real validator.
- **Both absence assertions were INVERTED, not deleted** —
  `policy::submit::the_live_proposal_inventory_is_the_policy_inventory` and
  `src/engine/tools.test.ts`'s "offers exactly the proposal surface the policy
  artifact authorises". Each now proves the served set equals what the
  artifact authorises, in both directions, with synonyms and the human's own
  `record_decision`/`resolve_commit_set` still forbidden.

**A trap this phase found and closed:** `propose_organize` is a hand-written
tool that predates this namespace and is not a policy op. A bare
`strip_prefix("propose_")` routes it to the mutation boundary; it escaped only
because its match arm came first, and arm order is not a security property.
`proposal_op_of` asks the table instead.

**Still not wired after this phase:** nothing dispatches ambient work
(`dispatch::claim` still has no production caller), so this is an ATTENDED

#### What a 27-agent adversarial review found, and what is left

Five attackers plus per-finding refutation. Eight claims survived; three were
fixed here, and **two of the survivors are why the switch must stay off.**

Fixed in this commit:

- **CRITICAL — `propose_append_observation` forged the ledger's actor.** Its
  payload is the server-canonical `ObservationRecorded` body, and
  `expand.rs`'s arm for it is the only one of twenty that passes the caller's
  `actor` through instead of stamping the run's. `reduce.rs` derives
  AUTHORITY from that actor, so an agent could mint a `TrustedHumanCapture`
  observation attributed to the human — LOW risk, auto-applied, no card. The
  predicate that should stop it, `trusted_observation_provenance`, is
  required by the row and evaluated NOWHERE; its declared owner
  `AgentObservationDraft` is dead code. **Fix:** `agent_facing: false` until
  the draft→recorded conversion exists.
- **Synthesized `intended_use`/`basis` defaults were the modal path** — the
  schema advertised only `[payload, targets, reason]`, so omission was
  normal, and the defaults understated stakes and asserted a cause nobody
  supplied. Both are required now.
- **The proposal path never met `knowledge::guard_agent_write`**, so an agent
  could patch `/fields/verified` — signing the review it exists to be checked
  by. Refused in `tool_propose`.

**M26.3d closed both of these.** The write-up below is kept as the record of
what was found and why the fix took the shape it did.

**CLOSED (M26.3d):**

1. **`targets` is not bound to `payload`.** CAS (`versions_current`) and both
   escalators (`target_has_attestation`, `lineage_fan_in`) read
   `proposal.targets`, while the mutation is expanded from `proposal.op`. An
   agent can declare a harmless target — a fresh id with
   `expected_version: null`, which reads as a creation — and mutate something
   else entirely, so **an attested Belief can be revised without becoming a
   human card.** `target_set_exact` only checks target CLASSES. The fix is a
   per-op extractor naming the ids an op touches, server-derived; there is no
   such function today, and inventing one per op in `mcp.rs` would be the
   second inventory this milestone forbids. It belongs in the schema layer
   beside `target_classes()`.
2. **`write_target` returns `None` for every proposal tool**, so `RunGrant`'s
   folder scope is never applied to them. Narrower than it sounds — the
   proposal surface writes through the ledger rather than to paths — but a
   scoped run is not scoped here, and the doc comment on `write_target`
   claims any future write "will be caught by
   `no_write_tool_escapes_the_scope_check`", which enumerates three hardcoded
   names and would not catch one.

### M26.3d — the target binding (this commit)

**The rule, in one sentence a reviewer can check:** for every `(class, id)` the
op's own expansion would ADVANCE, whose id the payload NAMES, `targets` must
contain that exact pair — otherwise `target_set_mismatch`.

- **Containment, not equality.** Extra declared targets stay legal: a target an
  op only reads keeps its version, and `commit.rs` is built to make a read
  legible as a read. Extra targets widen CAS and turn MORE escalators on, so
  they cost the caller and buy it nothing. Equality would also have broken
  seven shipped goldens that legitimately declare reads.
- **Payload-named, and this is the part three independent mappers all got
  wrong.** Relation ids are `sha256("cerebro-relation-v1\0" ++
  canonical_json([from,to,kind]))` and no tool hands a caller a way to compute
  one. Plain containment over the whole write set would have made
  `supersede_belief`, `split_belief`, and both merges **unproposable by any
  agent**. A server-derived id is also not an attack surface — it is a pure
  function of ids the payload names, which the rule does check.
- **The extractor already existed**, and the M26.3c handoff was wrong to say
  otherwise: `Expansion.write_targets` is exactly "the (class,id) pairs this
  plan advances". `write_targets_of` CALLS `expand` rather than re-matching on
  the twenty arms — a second match would be the second inventory, and the two
  copies would diverge precisely on the conditional arms
  (`merge_beliefs_exact` revises the survivor only when the basis differs) and
  the state-derived one (`revert_proposal` reads its steps from the stored
  plan). The cost is expanding twice per commit; the alternative is a
  predicate allowed to disagree with what actually gets written.
- **Home: `preconditions::check`**, under the predicate name the table already
  uses. Zero artifact churn — all 20 op rows already require `target_set_exact`
  and declare `target_set_mismatch`, which is already ledger-destined. Not the
  schema layer: `submit_proposal` returns on `validate()` failure BEFORE
  appending `proposal.submitted`, so a schema-home refusal is structurally
  incapable of producing a ledger record. Not the table stage: `ProposalFacts`
  carries no ids in either language, so teaching it ids means a TS twin
  including the relation hasher.
- Sorted `requires` puts `target_set_exact` before `versions_current`, so a
  card says "you did not name what you are changing" before "your version is
  stale" — and that order is the artifact's, not a branch order.
- **Companion fix:** `append_observation` and `cache_source` declared no write
  targets at all, so a binding rule would have exempted them by matching an
  empty set. Both now declare the Source, which the reducer really does bump.

`PREDICATE_OWNERS` moved from `M24.1 // the table's target-class stage` to
`M26.3 // classes: the table stage; ids: target_set_bound`.

Also closed: the scope tripwire `no_write_tool_escapes_the_scope_check` named
three tools and called itself total. It now partitions the WHOLE served
catalog into scope-checked and explicitly-exempt-with-a-reason, so a new tool
in neither half fails. The proposal surface is exempt by declaration: it writes
through the ledger, not to a path, and `RunGrant.scope` is a folder primitive
that cannot express "which Beliefs" — governing that is the policy table's job,
which it already does per op and per risk.

### M26.4c — the prompt and §92 containment (`a6b5791`)

### M26.4g — the retry bound at the boundary (`be9466a`)

`tool_propose` counts a run's attempts per piece of work and refuses a
resubmission the table forbids, BEFORE evaluating it. Three typed refusals:
`retry_not_permitted`, `retry_exhausted`, `retry_unchanged`.

**Six decisions worth not re-deriving.**

1. **The owner's notes are the OWNER's source, not a builtin.** The first
   draft registered `vault-files-v1` as a `SourceRegistration::Builtin`
   carrying `human_assertion`; the schema refuses that outright — authority is
   provenance derived from WHO, never a label on a service id. It now
   delegates to `capture::resolve_registration("human:owner")`, so a note
   typed in the app and the same note typed in an external editor are ONE
   source. Two identities for one person would make a single claim look like
   two, which is manufactured corroboration. `knowledge/` stays a `builtin`
   with `content_only`. Both are irreversible: `derive_item_id` and
   `derive_receipt_id` bake the source id into every identity.
   `capture::resolve_registration` and `source::resolve` both take an ORDINAL
   now — a first launch over a vault with a `knowledge/` bundle registers two
   sources in one batch, and two members claiming ordinal 0 would have one
   source's Observations pinning the other's registration.
2. **Exactly ONE Observation per receipt, structurally.**
   `IngestAssessed::validate_refs` wants `observation_event_ids` sorted and
   duplicate-free; `append_batch` mints random member ids and substitutes
   same-batch refs BEFORE validating. Two refs would pass about half the time,
   non-deterministically.
3. **A successor's dimensions are governed by its outcome.** THE defect this
   phase found: a `material_candidate` receipt could never be closed. The
   schema required a candidate to name a dimension and `outcome::close` clears
   the successor's by design — and with no deterministic mapper in this build
   EVERY material candidate queues, so that was the common case. Fixed in
   Rust, TS, and a new conformance vector; the two fixtures that could have
   caught it both happened to use `needs_semantic_judgment`.
4. **Counterevidence names its test.** `Candidate.disconfirming` became
   `Standing::{Uncontested, Contested}`, and `Contested` means "a live
   `contradicts` edge touches this belief", not "disagrees with this change" —
   the change has not been interpreted yet. The empty section reports which
   edge was walked. All-false was the one wrong answer available, because the
   prompt would then have asserted an absence nobody established.
5. **`agent::stream` has a completion signal.** `Tally::outcome` already
   computed `(RunOutcome, Option<Usage>)` and `meter::finish` discarded it.
   The receiver blocks on `recv()`, never `recv_timeout` — the elapsed
   watchdog bounds the run and sets the `aborted` flag the send reports, so a
   caller that timed out on its own would report an outcome the run never had
   and leave a live child behind. `Mode::Supervised` stops the meter
   finalizing: the ROUTE decides where items land, not the CLI's exit status.
6. **The residual is read from the SCHEDULER, not from the tick's own plan.**
   An item queued while the budget gate was shut stays `pending`, and the next
   catch-up correctly leaves it alone. A driver that only ran what it just
   planned would strand every item that ever waited a tick for budget. An item
   edited between assessment and run is skipped — the receipt describes exact
   bytes.

**Two smaller calls, in code:**

- `catchup::Queued` carries whether the ARTIFACT moved or only the normalizer
  did. A receipt claiming a file changed when only the rules did is a wrong
  answer in a portable log.
- `catchup::scan` returns what it could not read instead of `continue`-ing.
  The driver records an `ingestion_failures` row per name.

**Deadlocks avoided, both real and both structural.** `ingest::commit` exists
because `shadow::with_writer` holds a process-global mutex the MCP thread also
takes; `ingest::ambient` opens its OWN sqlite connection for the same reason
(`sink::with_sink` is a process-global mutex and `mcp.rs:857` takes it). In
both cases the rule is: never hold a process-global lock across a blocking CLI
run. Any future code that spawns a run must be read against that rule.

**Declared limits of this milestone** — each one is a passing test that will
FAIL when the limit stops being true, which is the correct behaviour:

- prose-only edits close as `non_material` (`normalize::snapshot` excludes the
  body by choice);
- `corroborates_existing_value`, `same_lineage`,
  `deterministic_proposal_available` and `residual_ambiguity` are all `false`
  with no producer, so every material change costs a run;
- `resolutions` is empty — M26.1's resolver runs per subject and an ingest
  window has no subject until the run finds one;
- `catchup::Plan.departed` is computed and not acted on: `item_key` IS the
  path, so a rename reads as a departure plus a new item, and closing departed
  rows would retire the history of every file anybody moved.

## M33.10 — the hub navigates itself, and the corpus grows an operational half (2026-08-15)

Owner feedback on the built hub, and both halves of it were fair.

**The hub borrowed Home's sidebar.** `status` was never in `SIDEBARLESS` — the
M33.3 plan step flagged exactly this ("add to `SIDEBARLESS` if the merge
changes its classification") and the check was made without acting on it. That
was survivable when the hub was one section and four doors; at five sections
it meant the page was framed by a types-and-views list describing the RECORD
corpus, which has nothing to say about runs, budgets or queued proposals.
`status` joins the sidebarless destinations and carries `src/status/StatusNav.tsx`
instead: its own contents, driving the `section` the Selection already held,
with the active row OBSERVED via `IntersectionObserver` rather than tracked
from the last click (the page is one scroll container; a nav that highlighted
only what was clicked would be wrong most of the time). No counts on it — the
M8 rule that kept a badge off Knowledge and History.

Two defects found doing it:

- **The nav rows first carried `data-section`**, colliding with the attribute
  that addresses the SECTIONS and making every section locator in the suite
  ambiguous — 20 e2e failures, all one strict-mode violation. Nav rows use
  `data-target`. One attribute, one meaning.
- **The content column was still centred** as if it filled the window, leaving
  a ~245px dead gutter beside a 200px nav. Left-aligned; the max-width stays,
  because these are sentences to read.

**The operational surfaces had no corpus.** `demo-vault/` is the golden corpus
for every RECORD surface, but runs, the review queue, the budget meter, the
attention lanes and the convergence window all live in SQLite or the ledger —
neither of which the browser has — so the mock answered every one of them
empty or refused. Defensible while they were doors; not once M33 made them
bodies. A hub whose five sections all say "nothing yet" cannot be evaluated,
designed against, or demoed.

`src/lib/demoOperational.ts` supplies that half, and every fixture in it earns
its place by exercising a branch some component has: `actor: null` →
"unattributed"; `usage_state: 'unknown'` → "unknown" over its zero columns;
no cost rows → "not recorded"; recorded rows with one `estimated` → the
estimate marked; a run with proposals still undecided → the door to the needs
section; all three constructs so the actor filter has real options; HIGH-and-
stale and CRITICAL-and-diff cards; an applied-but-undoable change. Dates are
`VAULT_TODAY`'s, so the operational story sits inside the one the vault tells.

`resetOperational()` restores it and `resetMockFs()` calls it, so one reset
puts the whole mock back. **Empty is now a case a spec STAGES rather than one
it inherits** — two `status.spec.ts` assertions became explicit seeds.

One trap worth recording: `resetMockFs()` runs at module load, so folding the
operational reset into it reached `const`s declared further down and threw
`Cannot access 'review' before initialization` — a temporal-dead-zone error
`tsc` cannot see. File seeding is now `seedFiles()`, called at init; the
exported `resetMockFs` composes both and is safe once the module has finished
evaluating.

`NoteBodyEditor`'s debounced-write test failed once in a full run during this
work and passed 3/3 alone and twice more across full runs. It is the
load-sensitive flake its own comment describes, not a regression.

## Working rules for a fresh context

- **Verify before you claim.** Run the gate; quote the counts. The last known
  green numbers are recorded in each phase's commit message.
- **The schema is the tripwire.** Two real ordering bugs in M25 were caught by
  foreign keys and CHECK constraints, not by tests. If SQLite refuses
  something, read it as a design answer before reaching for `PRAGMA`.
- **Never mirror a rule.** If a rule needs to exist in Rust and TS, it belongs
  in a shared artifact with a digest, or in the conformance vectors.
- **Held is a real answer.** Whenever the honest options are "assume consumed"
  or "assume pending", the third answer — hold it and ask the owner once — is
  the one this milestone keeps choosing. Follow it.
