# M34.2 — Durable schedules: the ledgers move to Rust, unattended runs face the gate

**Spec:** `docs/superpowers/specs/2026-08-17-agent-platform-design.md` §7 (M34.2 row), §8.3.
**Branch:** `m34-agent-platform`. Written after recon on 2026-08-20; M34.2.1 (honest runs:
could-not-tell log rows, `dueAt`, "late is not failed") already landed in `284c43f`.

## What the spec asked for, corrected by recon

The spec row says: move `jobQueue` / `parseSchedule` / `diffEntries` and the three
localStorage ledgers into Rust; catch-up on launch marked LATE; lane_registry migration;
reconcile with `ambient.rs`'s lease. Three corrections, found in the tree:

1. **No lane_registry migration is needed.** `scheduled`, `agent`, `refresh`, `stale`,
   `schema` have been seeded since M25 (`schema::LANES`, `runtime/mod.rs`
   `seed_and_validate_v3`). The job kinds map 1:1 onto existing lanes.
2. **`jobQueue` / `parseSchedule` / `diffEntries` stay in TS.** They are pure
   derivations over the renderer's scan. What must not live in the renderer is
   **state** (the ledgers — a webview data wipe re-fires every schedule: duplicate
   spend) and **accounting** (see 3). The settled product decision is app-lifetime
   execution with catch-up on launch — a Rust tick would still be app-lifetime, so
   relocating the derivation buys nothing that a DB-side *claim* doesn't: the claim
   makes two windows safe, the DB makes reinstalls safe, and the derivation's inputs
   (entries, concepts, events) already live where the scan lives.
3. **§8.3 is answered: it was a gap, not intent.** `dispatch.rs` books every
   renderer-started run `mode='attended', lane='agent'`, so scheduled Agent records
   are metered but never budget-gated. Fix: unattended renderer runs go through
   `dispatch::claim` — zero items, the job's real lane, the agent's actor — and are
   finalized as `Mode::Ambient`. `claim` already admits an empty item list
   (`pending.is_empty() && !items.is_empty()` deliberately passes), already gates on
   the day budget AND the actor's pause, and already records a Deferral row nobody
   can lose. This IS the "reconciliation with the single lease": the job runner
   becomes another client of the same dispatcher, so ingest and schedules share one
   budget, one concurrency ceiling, one deferral record.

## Tasks

### M34.2.2 — `job_ledger` (schema v16) + claim semantics

- `job_ledger (vault_id REFERENCES vault_registry, ledger CHECK IN
  ('attempts','skillRuns','triggerRuns'), key, run_key, recorded_at)`,
  PK `(vault_id, ledger, key)`.
- `runtime/job_ledger.rs`: `read_all(vault) -> {ledger -> {key -> run_key}}`;
  `claim(vault, ledger, key, run_key) -> bool` — false iff the stored `run_key`
  already equals this one (that exact fire was answered — by another window or an
  earlier session); an OLDER stored key updates and returns true. `stamp` for
  `triggerRuns` (a cooldown clock, last-write-wins, no verdict).
- Tauri commands `job_ledger_read`, `job_ledger_claim`, `job_ledger_stamp`,
  `job_ledger_import` (bulk, for M34.2.3's one-time migration — never overwrites a
  key the DB already holds).
- Mock parity in `mockIpc.ts`: backed by the existing localStorage keys, so the
  browser build keeps today's persistence and the e2e mock keeps its inspectability.

### M34.2.3 — the renderer reads what Rust remembers

- `useJobRunner` hydrates the three maps per vault before the queue may fire
  (a `ledgersReady` gate — an unhydrated map looks like "nothing ever ran", which is
  the launch-storm bug the ledgers exist to prevent).
- The consume points call `job_ledger_claim` and READ the verdict: false → the job is
  skipped without spawning (someone else ran it). True → spawn, and the uiStore map
  is updated so the derivation catches up. `recordTriggerRun` → `stamp`.
- One-time import: when the DB-side ledger is empty and localStorage holds entries
  for this vault, push them via `job_ledger_import`. A recovered/fresh DB re-imports
  — old fire keys suppressing re-runs is exactly the desired failure mode.
- localStorage stays the mock backend's store; in Tauri the DB is the truth.

### M34.2.4 — unattended runs face the gate

- `run_agent` with `attended: false` and a registered vault: `dispatch::claim`
  (lane = job kind, items = `[]`, actor = the record's actor, reservation = the
  shipped ambient defaults). `Deferred(reasons)` → the command returns a typed
  `{ deferred: [...] }` instead of a run; the runner logs ONE run-log row
  ("deferred by budget: …" / "paused") per (job, runKey) and leaves the fire key
  unconsumed — deferral must never eat the period. `Started(lease)` → the Meter runs
  `Mode::Ambient` under `lease.run_id` with the lease's elapsed watchdog armed, and
  `dispatch::finalize` closes the books into `budget_days`.
- Attended chat stays `attended` — metered, never gated — including addressed turns.
- Handoff runs (`start_handoff_run`) keep their current booking; the root-ceiling
  chain gate is M36's consequence work, not this slice (deferral named in spec §7).
