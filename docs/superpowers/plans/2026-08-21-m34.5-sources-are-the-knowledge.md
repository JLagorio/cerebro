## What the spec asked for, corrected by recon

The spec row names four items. Two are already true and one belongs to later
milestones by the spec's own words:

1. **"Connector setup UI (today: hand-edit connectors.json)" — stale.**
   `src/app/ConnectorSettings.tsx` (M13.3) has been that UI for months: add,
   enable/disable and remove entries, http and stdio transports, per-machine
   stdio approvals outside the vault. Headers/env stay file-edited BY DESIGN —
   credentials never enter cerebro. Nothing to build.
2. **"Promote cache_source records out of knowledge/" — never true.**
   `SOURCES_DIR` is top-level `sources/` on both sides
   (`vault::write::SOURCES_DIR`, `engine/ingest.ts:303`), and always was — the
   sibling-of-knowledge comment in ingest.ts says exactly that. Nothing to move.
3. **"is_knowledge_path's 8 leak sites" — enumerated, none is this milestone's.**
   Rust: two capture-valve sites in lib.rs (the gate M36 moves, per the M36
   row), four inside knowledge.rs (the guard's own body), four in mcp.rs
   (`write_concept`'s guard, `knowledge_about`'s filter, the M34.4 read
   boundary) — the knowledge agent's own tools, which M35 relocates with the
   agent. TS: `okf.ts` and the `knowledge/*` components — M35's "private read
   model" by the spec's own fate table. No GENERIC surface routes on the
   string. The count was pre-M33a recon; the consolidation already happened.
4. **"Source Monitor surfaces staleness on the source record" — the real gap.**
   Concept staleness renders in three places (KnowledgePanel, ThreadView,
   EntityDossier); a SOURCE record's freshness renders NOWHERE — `stale_after`
   and `fetched_at` are invisible in the detail panel, so "this copy of the
   Jira ticket is three weeks past its refresh date" is a fact the vault holds
   and no surface says.

"Connection triggers are noticed, not pushed" is already the architecture: the
Source Monitor never fetches (its module header makes that architectural), a
refresh WRITES the source file, the write mints a `VaultEvent`, and `when:
changed in sources` is ordinary trigger vocabulary. What is missing is a test
pinning the loop as designed behavior rather than a coincidence of parts.

## Tasks

### M34.5.2 — `sourceFreshness` derivation (engine)

Pure, in `engine/ingest.ts` beside `SOURCES_DIR`. Gated on the fetch
bookkeeping PROPERTIES (`fetched_at` / `stale_after`), never on `type:
Source` — the no-type-routing rule; a record with fetch bookkeeping is a
cached copy wherever it lives. Returns null for everything else so the
detail panel self-gates. The honesty rules, load-bearing:

- Absent `stale_after` ≠ fresh: it is **"no refresh date set"** — nobody said
  it expires, and the monitor's own header forbids inventing a default.
- Absent `fetched_at` with a `stale_after` ≠ zero: **"fetch not recorded"**.
- `stale_after <= today` (local date words, same comparison the refresh lane
  uses) → stale, saying since when.

### M34.5.3 — the record says it (detail panel)

`SourceFreshness` line in `DetailPanel` between properties and knowledge:
renders null without bookkeeping, one sentence with it. Tested per state.

### M34.5.4 — the noticed-not-pushed loop, pinned

`engine/jobs.test.ts`: an agent watching `when: changed in sources` is woken
by a refreshed source file's event — the whole connection-trigger story in
one deterministic test.
