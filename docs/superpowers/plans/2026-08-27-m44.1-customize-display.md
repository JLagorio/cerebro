# M44.1 — Customize display Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A per-TYPE persisted "Customize display" config for the record detail panel — empty-property fold default, a file-path row, a body toggle — stored on the Type doc's frontmatter under `display:`, edited from a drill-in inside the record-actions menu, honoured by `RecordProperties`/`DetailPanel`, with reset-to-defaults.

**Architecture:** `display:` joins `views:`/`statuses:` as a reserved Type-doc frontmatter key. `buildSchema` parses it tolerantly into `TypeDef.display` (a fully-defaulted `DisplayConfig`, so consumers never null-check), a `setTypeDisplay` action in `typeActions.ts` writes deviations-only (all-default = `display: null`, which IS the reset), and the UI reads it via the schema — `RecordProperties` needs zero prop changes across its three call sites. Per-field hiding REUSES `FieldDef.visibility` (already persisted, already guarded) — the drill-in surfaces eye-toggle rows that write through the existing `setFieldConfig`.

**Tech Stack:** React 19 + Zustand + the existing `patchFrontmatter` IPC (key-agnostic on both Rust and mock backends — zero backend work).

**Plan-level decisions (spec §4 loose ends this slice resolves):**
- **Hidden-field keys are NOT a new list.** `FieldDef.visibility` (`show | hide_when_empty | hide`, `src/engine/types.ts:110-128`) already answers "is this field hidden on this type", persisted on the Type doc and edited via `PropertyMenu` → `setFieldConfig`. A second `display.hidden: []` list would be two answers to one question. The Customize-display drill-in surfaces the EXISTING mechanism as toggle rows; the `display:` object carries only the three panel-level booleans that have no mechanism today.
- **No width preset.** Spec §5 decided device-local ephemera stays in uiStore and names `detailWidth` as the example; the panel already has drag-resize plus the widen/narrow button. Adding a per-type width would fight the user's own resize. Deviation from the spec's M44.1 bullet list, recorded here.
- **Scope of each boolean:** `showEmpty` applies wherever `RecordProperties` renders (DetailPanel, DocPage full-page record, InboxPage) since it lives inside that component. `showBody`/`showFile` apply to the peek `DetailPanel` only — DocPage's body IS the page and hiding it there would be absurd; Inbox is a triage form.
- **Frontmatter spelling is snake_case** (`show_empty`/`show_file`/`show_body`), matching the `full_width` house style (`DocPage.tsx:246`). The TS type is camelCase.
- **Untyped records** (`entry.type === null`) have no Type doc: the menu entry does not render, and consumers fall back to defaults.
- **Defaults = today's behaviour:** `showEmpty: false` (the fold), `showFile: false` (no file row exists today), `showBody: true`.

Serializer beside `parseDisplayConfig`:

```ts
/** DisplayConfig → the `display:` frontmatter value. Deviations only; all
 * defaults = null, which patchFrontmatter spells "delete the key". */
export function serializeDisplayConfig(d: DisplayConfig): Record<string, unknown> | null {
  const out: Record<string, unknown> = {};
  if (d.showEmpty) out.show_empty = true;
  if (d.showFile) out.show_file = true;
  if (!d.showBody) out.show_body = false;
  return Object.keys(out).length === 0 ? null : out;
}
```

Action, cloned from `setTypeViews` (`typeActions.ts:564-589`) with the same `findTypeDoc`/`guardEditable`/`ensureTypeDoc` skeleton:

```ts
/**
 * Persist the record panel's per-type display config onto its Type doc
 * (M44.1). Deviations only — a type left at the defaults carries no
 * `display:` key at all.
 */
export async function setTypeDisplay(
  listing: { name: string; docPath: string | null },
  display: DisplayConfig,
): Promise<boolean> {
  const { entries, patchFrontmatter } = useVaultStore.getState();
  const toast = useUiStore.getState().toast;
  const doc = findTypeDoc(entries, listing.name);
  if (!guardEditable(doc, listing.name)) return false;
  const serialized = serializeDisplayConfig(display);
  try {
    if (doc === null) {
      if (serialized === null) return true; // nothing to write and nowhere to write it
      await ensureTypeDoc({ name: listing.name, docPath: null }, { display: serialized });
    } else {
      await patchFrontmatter(doc.path, { display: serialized });
    }
  } catch {
    toast(`Couldn't update ${listing.name} display`);
    return false;
  }
  return true;
}
```
