# M45.1 — Layout engine + record surfaces Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The `layout:` Type-doc vocabulary (heading strip + property groups), its atomic persistence door, and the REAL record surfaces rendering it — so M45.2's editor previews truth.

**Architecture:** `layout:` is a new reserved Type-doc key parsed tolerantly in `schema.ts` (M44.1 `display:` pattern), resolved against the field roster by a pure `resolveLayout` in a new `src/engine/layout.ts`, rendered by `RecordProperties`/`DocProperties` (groups) and a new `HeadingProperties` strip (DocPage + DetailPanel), and written — together with `display`/`tabs`/field deltas — through ONE new `applyTypeLayout` door in `typeActions.ts`.

**Tech Stack:** existing only — React 19, Zustand stores, vitest + testing-library. No new deps.

**Spec:** `docs/superpowers/specs/2026-08-28-cerebro-m45-layout-editor-design.md` §4, §3.4, §5(M45.1), §6.

## Decisions this plan locks (record deviations in this file if review overturns one)

- **Claim order is parse-time law**: a field name appears at most ONCE across `heading` + all `groups`; the first claim wins, later claims are dropped at parse. Downstream code never dedups.
- **Group ids** mint two-pass (`group-${n}`), exactly `parseTabList`'s shape (views.ts:960-987) — a declared id is never stolen by a minted one. Ids matter to M45.3's drag/editor even though nothing per-record keys on them yet.
- **`rest` renders after named groups** (a newly added field lands visibly at the bottom of the arranged stack), and the hidden-properties expander stays GLOBAL — one fold at the bottom, not one per group.
- **Grouped mode disables the property-reorder grip** in the panels (declaration order still owns column order; ARRANGEMENT is the editor's job in M45.3). Flat mode (no layout) keeps today's grip exactly.
- **Empty groups survive resolution** (the renderer skips them; M45.2's editor shows them as drop targets).
- **The View details expander** exists only where the body does: DocPage `overview` tabs and the DetailPanel. A `properties` tab always shows the full stack; a `sections` tab shows the strip only. Collapsed-by-default when a heading strip exists. Local state — a lens, never persisted.
- **Declaration order is untouched by layout** — `layout` places, `fields:` declares. `applyTypeLayout` takes NO order delta (YAGNI: groups place).
- **`applyTypeLayout` merges deltas onto the RAW `fields` mapping** (setFieldConfig's grow-the-shorthand idiom, typeActions.ts:502-505). It never rewrites the whole mapping from `FieldDef` — recon found `fieldToSpec` (typeCatalog.ts:202-224) drops `visibility`/`dateFormat`/`timeFormat`, and a hand-edited vault may carry keys we don't model. Task 3 fixes `fieldToSpec` for the `added` path only.

- [ ] **Step 2: Run** — FAIL (module missing).
- [ ] **Step 3: Implement** `src/engine/layout.ts`:

```ts
export interface ResolvedLayout {
  heading: FieldDef[];
  groups: { id: string; name: string; fields: FieldDef[] }[];
  /** Declared fields no container claimed, declaration order. Renders after
   * the named groups so a freshly added field lands visibly. */
  rest: FieldDef[];
  /** Nothing resolved to a placement — render the pre-M45 flat stack. */
  flat: boolean;
}
export function resolveLayout(layout: LayoutConfig, fields: FieldDef[]): ResolvedLayout
```
Map names → defs via a `Map` of the roster; skip unknowns (dead pointers render as nothing — pruning happens on the next Apply, not on read); `flat = heading.length === 0 && groups.every((g) => g.fields.length === 0) ? …` — precisely: flat when the resolved heading is empty AND every resolved group is empty (an all-dead layout must not disable the grip or the flat path). Parse already guarantees no duplicate claims.
