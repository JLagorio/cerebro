# M45.4 — View tabs Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A record tab backed by a database view — Notion's "Link existing data source" (screenshot 4): "View of: <database>", optional saved view, optional relation scoping — rendered on the record page and honest when its source dies.

**Architecture:** `TAB_CONTENTS` gains `'view'`; a view TabDef carries a source pointer (reference-never-copy, the dashboard widget doctrine). Resolution reuses `resolveSurface` with synthetic selections (the dashboard ViewBlock path); `scope: related` injects an `any_of` filter built from the relation field targeting the host type (the M44.3 drilldown family). DocPage grows a fourth swap arm; RecordTabs' NewTabForm grows the "View of" drill-in.

**Spec:** `docs/superpowers/specs/2026-08-28-cerebro-m45-layout-editor-design.md` §3.5, §7 (pinned pointer shape + rosters + doctrine).

---

## Decisions this plan locks

- **Pointer shape on disk** exactly spec §7: `content: view` + `source: { type } | { list, collection? }` + optional `view` (view id) + optional `scope: related`. Parse keeps an unresolvable source verbatim (the tab id may be load-bearing); the RENDERER shows the broken state — unavailable is never empty. Unrecognized `content` still falls back to `'sections'`; a `view` tab MISSING a source entirely parses with `source: null` and renders broken (never dropped — dropping eats the declared id).
- **Scope is capability-gated, never type-name-routed**: the toggle exists iff `relationFieldTargeting(sourceType, hostType, schema)` finds a relation/person field on the SOURCE type whose `target` is the host's type; default ON when offered (Notion's project→tasks case). `scope: related` with no such field at render time = the broken-state card naming the missing relation, not silently-all.
- **Related matching** goes through the reverse index the relations engine already maintains (verify `backlinksFor`/relation resolution in `src/engine/relations.ts` — the M45.4 recon step); the injected filter is `{ field, op: 'any_of', values: [host] }` in the M44.3 drilldown's construction, ANDed onto the view's own filters via the widgetEntries layering idiom.
- **The record page embed reuses the dashboard's rendering path**: extract the resolvable core of DashboardView's ViewBlock (resolve → hasBlocks guard → surface → ViewCanvas embedded) into a shared component both consume — the review-blocking alternative is a second copy of BrokenBlock/resolution logic. A record tab cannot show a dashboard (hasBlocks guard carries over verbatim).
- **The editor canvas does NOT live-embed view tabs**: the inert preview renders the tab strip (names) and, for an active view tab, a quiet placeholder block naming the source ("View of Tasks — shown on the record page"). A live ViewCanvas inside the inert canvas is weight without fidelity; recorded as the deliberate M45.2-style honest omission.
- **Tabs are still edited on the real record page** (RecordTabs' strip — M44.5's home); the editor's Structure tiles keep their M45.2 role. No second tab-editing surface.

## Tasks

### Task 1: Engine — the view tab vocabulary
`TAB_CONTENTS + 'view'`; TabDef grows `source?: { type: string } | { list: string; collection?: string | null } | null`, `view?: string`, `scope?: 'related'`; parseTabList arms (tolerant-by-value; source kept verbatim when unresolvable-shaped; scope only `'related'`); serializeTabList emits the new keys only when set; RecordTabs' `TAB_KINDS` untouched here (Task 3). Tests: round-trips, garbage tolerance, missing-source kept, the two-pass mint indifferent to the new keys.

### Task 2: Engine — resolution + related scoping
`src/engine/viewTab.ts`: `resolveViewTab(tab, host, entries, schema, views)` → `{ kind: 'ok', surface, presentation } | { kind: 'broken', reason }` — reasons for: missing source, dead list/type, dashboard-in-record (hasBlocks), `related` with no qualifying relation. `relationFieldTargeting(sourceType, hostType, schema)`. The related filter construction + layering (recon the M44.3 drilldown filter builders and reuse, not copy). Frozen-input tests per case incl. the honest-broken sentences.

### Task 3: RecordTabs — the add-view flow
`TAB_KINDS` gains the view tile; NewTabForm drills into "View of" (roster: `listTypes` + `useVaultStore(s => s.views)`, the dashboard "Saved view…" submenu's exact labeling incl. the `collection::id` keying), optional view picker (source's views; default first), the scope toggle (offered/gated + default-ON rule), Add view. Editing an EXISTING view tab's source/scope goes through the tab's menu (a "Change source…" item reopening the same drill-in). Tests per the RecordTabs suite idiom.

### Task 4: DocPage — the fourth arm
`content === 'view'` renders the shared embed component (Task 2's resolution + the extracted ViewBlock core); `showsEditor` stays false (the M44.5 editor-reset key untouched — assert); broken states render the card, never empty; `page-properties` does NOT render on view tabs (the tab IS the content). Editor canvas: the placeholder block for view tabs. Tests: swap, broken source, related scoping end-to-end with a two-type fixture (host + tasks with a relation), stale `selection.tab` fallback unchanged.

### Task 5: Golden corpus + e2e + gate
Corpus: give a demo-vault type a view tab wired to an existing List (recon which; full e2e first to find churn); e2e: open record → view tab → rows scoped to the host record → unlink the source in the mock fs → broken card (honest, not empty). Full gate; the slice write-back appended to this plan; push.
