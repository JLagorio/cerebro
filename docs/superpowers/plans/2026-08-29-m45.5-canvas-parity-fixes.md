## The four defects (user's words → what lands)

1. "tabs are on top. cant add, edit, rename, or remove tabs." → The strip renders FIRST in the canvas (above the heading) and is inert with no-op handlers. Fix: heading block first, tab strip second (Notion's order), and the strip goes LIVE against the draft — add, rename, remove, reorder, duplicate, Change source, all staging `draft.tabs`.
2. "each section should have visible zones boundaries like notion" → Chrome is hover-only (ring + name chip at opacity-0). Fix: every block wears a PERSISTENT boundary — visible border + always-visible header label, Notion's titled-panel anatomy.
3. "No blue PLUS button to add new sections like notion" → Add section hides in the popover footer. Fix: a circular cortex + button on the canvas (below the last group) that mints a group and opens its editor. The popover footer entry stays — two doors, one editor.
4. "Adding, removing and editing a sections contents should be through the floating panel… that's also how we move properties within a section, on hover theres a draggable icon" → The panel exists but rows cannot reorder. Fix: hover drag grips on the popover's field rows; dragging reorders WITHIN the container via `moveField` with a real index. This closes the recorded within-heading-reorder limitation.

## Decisions this plan locks

- **Canvas order** (Notion screenshot 2): Heading → tab strip → group blocks → rest ("Properties") → Content → file path. Simple structure (`tabs: []`) still renders no strip.
- **The strip is LIVE, the tab CONTENT stays inert.** RecordTabs mounts outside `InertContent` with real handlers: `onChange={(next) => update({ tabs: next })}`, `onSelect` into new local canvas state `activeTab` (fallback to first when the id dies — RecordTabs' own idiom), `hostType={typeDef.name}` so a new view tab's scope toggle gates correctly. The view-tab placeholder follows the ACTIVE tab now (the first-tab-only limitation closes — delete its decision comment, it is falsified). Dialogs RecordTabs raises (rename, delete-confirm, NewTabForm, Change source) work as on the record page; they layer over the fullscreen Dialog via the existing popover/layer system.
- **Persistent boundaries**: each BlockShell gets `border border-n-200 rounded-md` (DS quiet border) always, plus a persistent header label — the shell's label chip becomes always-visible (drop `opacity-0 group-hover…` on the chip; keep the cortex ring as the hover/focus upgrade). The inner `GroupLabel` inside canvas group content is REMOVED (one label per zone — the shell header IS the label now; the real page keeps GroupLabel, this is canvas-only). `ShellEmptyHint` drops its own GroupLabel line for the same reason and keeps only the hint sentence.
- **The + button**: one circular button (`Icon plus`, cortex-600 bg, white ink, centered, ~28px) after the last `groupslot` DropSlot, before the rest shell. Click = `addGroup` via the popover's exact staging (`mintGroupId` against all draft ids, append, `onOpenGroup(minted.id)` → opens the new group's editor anchored to its fresh shell — the lazy anchor map already handles same-commit mounts). Keyboard reachable (a real `<button>`, aria-label "Add section").
- **Panel row reorder**: grips on GroupEditorPopover rows for `heading` and group containers ONLY — `rest` is derived/roster-ordered, reorder there is a promise the model cannot keep, so rest rows render no grip (honest absence). Use the repo's `useSortableList` idiom (single-axis) with its own DndContext INSIDE the popover (nested contexts don't collide; the canvas context never sees these drags). Drop commits `moveField(layout, name, { container, index })` with the same past-source slot decrement the canvas handler applies. Rows show the grip on hover (`group/row` + opacity pattern, matching canvas grips).
- **Spec re-amendment** (same commit as Task 2): §3.5 gains "RE-AMENDED 2026-08-29: user directive — the editor's strip is LIVE against the draft (add/rename/remove/reorder/source). The record page's strip remains the vault's editing surface; the M45.4 'one tab-editing surface' ruling is reversed by the product owner."

**Plan-text deviation:** Task 4 applies NO decrement — `useSortableList.onReorder`
already reports a post-removal index (unlike dnd-kit's raw visual slot, which is

**Decisions and deviations:**

- The two **Plan-text deviations** above are the record for Task 4's index
  handling: no decrement (`useSortableList.onReorder` already reports a
  post-removal index), and a resolved→config index-space conversion by the
  following NEIGHBOUR instead. Both are stated in place in
  `GroupEditorPopover.tsx`; they are not restated here.
- **Tabs are edited in the editor** because the product owner reversed
  M45.4's "one tab-editing surface" ruling on 2026-08-29. Spec §3.5 carries
  the re-amendment; this is a directive, not a review finding, and the two
  strips stage into different stores (the record page writes the vault, the
  canvas stages the draft) so they cannot race.
- **`--text-inverse` was reused, not twinned.** The + button's ink defect
  wanted a token for "ink on an accent fill"; the Tailwind bridge already
  names one, and minting `--on-accent` beside it would have been a second
  name for the same value — the kind of twin the policy-as-data rule exists
  to prevent. `text-n-0` was the wrong reach precisely because the neutral
  ramp inverts.
- **`rest` rows are gripless by design.** Rest is derived and roster-ordered
  and `moveField` ignores the index it is handed there, so a grip would move
  the icon and nothing else. The absent affordance IS the honest report of
  an absent capability (the empty cell is held open so rows still line up).

**Known limitations — carried forward:**

- The canvas still does **not live-embed view tabs**; the active view tab
  gets a one-line placeholder naming its source. Unchanged from M45.4
  (weight without fidelity), and the placeholder now follows the ACTIVE tab
  rather than the first.
- The **Simple tile reseeds `[Overview]` and discards richer tab sets**
  without a confirm — view pointers are unrecoverable except by Cancel.
  M45.2-era behavior, still a follow-up candidate.

**Known limitation — NEW, from the Task 2 review:**

- The canvas renders the **group blocks, rest and Content beneath a
  `sections` or `view` tab's placeholder**, although the real record page
  skips the property stack entirely for those tab contents (DocPage's
  `content !== 'sections'` gate, extended to view tabs in M45.4). The canvas
  is a LAYOUT canvas, not a page preview: those blocks are the thing being
  arranged, and hiding them behind a tab selection would take the editing
  surface away from the user standing on the wrong tab. Recorded rather than
  fixed, because the reviewer is right that it reads as a fidelity gap and
  the next reader deserves the reason.
  - **CLOSED by M45.6 Task 4** (2026-08-29). The reason above rested on a
    premise M45.6 removed: a section had no tab of its own, so the blocks
    beneath the strip were the ONLY editing surface and hiding them would
    have hidden the whole layout. Now a section belongs to a tab, the canvas
    resolves through `layoutTabScope`, and a `sections`/`view` tab shows its
    OWN content — the source placeholder or a free-text stand-in — with the
    property zones, rest and Content standing down. Nothing is taken away:
    every section is reachable from the tab that holds it, and "Move to tab…"
    in the group editor is the door between them.
