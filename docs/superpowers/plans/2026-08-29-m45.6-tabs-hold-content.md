# M45.6 — Tabs render, and tabs hold things Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close the two defects the user found testing M45.5 (2026-08-29): the tab strip never renders in the DETAIL PANEL, and nothing can be placed INTO a tab — a tab picks a content kind, but property groups are global, so the customizer offers no way to say "this section belongs to this tab".

**Architecture:** One new field — `LayoutGroup.tab?: string` — makes a section belong to a tab (as built: the key is ABSENT when untabbed, never `null`; `setGroupTab` takes `string | null` to spell clearing, but the stored shape has no null). Absent/null keeps today's behavior exactly (the group shows on the first property-bearing tab), so every existing vault is unchanged and no migration exists. `resolveLayout` gains a tab argument; the record surfaces and the editor canvas both filter through it. Separately, `DetailPanel` grows the tab strip DocPage already has, with the same four content arms in panel geometry.

**Spec:** `docs/superpowers/specs/2026-08-28-cerebro-m45-layout-editor-design.md` §3.5 (tabs) + §4 (`layout:` vocabulary), extended here. The M45.5 write-back's recorded omission — "the canvas still stacks group blocks, rest and Content under a sections-or-view tab placeholder" — is CLOSED by Task 4, not carried.

---

## The two defects (user's words → diagnosis → what lands)

1. **"the tabs dont render in the UI"** — the user is looking at the DetailPanel (the side peek). `grep RecordTabs src` finds exactly two non-test mounts: `DocPage.tsx:691` and the editor canvas. **DetailPanel never mounts it**, so a type's tabs are invisible on the surface a record row opens into. Fix: Task 2.
2. **"thers no way to put anything in the tabs in the customizer"** — `TabDef.content` is a closed kind (`overview | properties | sections | view`) and `LayoutConfig` is global: `{heading, groups}` with no tab dimension. Selecting a tab in the canvas changes nothing because the canvas has nothing per-tab to show. Fix: Tasks 1, 3, 4.

## Decisions this plan locks

- **A section belongs to a tab, and the heading does not.** `LayoutGroup` gains `tab?: string`. The heading strip stays global — Notion's own heading block sits ABOVE the tab strip (user screenshot 2), and ours already renders on every tab (`DocPage.tsx:724-741`).
- **Absent is the default tab, never "no tab".** A group with no `tab` renders on the first tab whose content is `overview` or `properties` (the "property-bearing" tabs). This is exactly today's behavior for every existing vault — zero migration, and a hand-written `layout:` with no tabs still works.
- **A tab id that no longer exists is a dead pointer, not a hidden group.** If `group.tab` names a tab the type no longer has, the group falls back to the default tab (visible), never vanishes. Same doctrine as dead field pointers: absent is never zero, and a group the user cannot see is a group they cannot recover.
- **`sections` and `view` tabs hold no groups.** Their content IS the tab (free text / an embedded database); `DocPage.tsx:754-755` already skips the property stack for both. The group editor refuses to move a section onto one, naming why.
- **`rest` stays global** — it is the derived remainder of the roster and has no tab dimension; it renders on property-bearing tabs as today. Recorded, not hidden: a section is the unit you assign to a tab.
- **DetailPanel is a peek, so its tab selection is LOCAL state**, not the selection/URL (DocPage rides `navigate({kind:'doc', tab})` because a page IS a place; a peek is not). Falls back to the first tab when the id dies, the canvas's own idiom.
- **The editor canvas swaps by the selected tab** (M45.5 already gave it `selectedTab`): the group blocks shown are the active tab's, the + button adds a section TO the active tab, and a `sections`/`view` tab shows its own content instead of the property zones — closing the M45.5 recorded fidelity gap rather than carrying it.

**Decisions:**

- **The `LayoutTab` seam.** `resolveLayout` holds no tab roster and must not
  learn one, so the caller reports `{ id, isDefault, canHoldSections }` and
  `typeCatalog.layoutTabScope` builds it from a type's `tabs:` — one place
  decides "which tab is default", and three surfaces (page, peek, canvas)
  read the same answer. The canvas is a PREVIEW of the other two; a second
  derivation is exactly how a preview starts lying.
- **`canHoldSections` is a REQUIRED predicate, not an optional one and not a
  roster.** Optional-with-a-permissive-default would read as "every tab can
  hold sections", and a section pointing at a tab that cannot would silently
  vanish — the one outcome the doctrine forbids, and it would fail INVISIBLE.
  A roster would hand the engine ordering, counting and content kinds it has
  no business with. It answers about ONE id, and the FALLBACK stays the
  engine's: the caller reports a fact it can see, `resolveLayout` alone
  decides what that fact means. It is asked BEFORE the id match, so a
  stranded section has exactly one home rather than two.
- **`flat` is GLOBAL by necessity** (a981ea1). Computed from the tab-filtered
  groups it re-opened a double render: the consumers' flat branch ignores
  `groups`/`rest` and stacks the WHOLE declared roster, so a tab holding no
  section of its own reported flat and re-rendered — loose, and editable in a
  second place — a field its section already shows on another tab. It needs
  only an empty heading plus sections placed elsewhere, which is the normal
  outcome of this feature. Consequence, and the right one: such a tab takes
  the non-flat branch and loses the roster's reorder grip. Once anything is
  placed anywhere, the config owns the order.
- **`rest` and `heading` stay global.** Rest is the remainder of the ROSTER,
  so a field another tab's section claims is not also loose here (the
  resolve-before-filter ordering is what makes that true). The heading
  renders above the tab strip — Notion's own heading block does — so it has
  no tab dimension to take.
- **Both fallbacks live in the engine and land a section exactly once.** A
  dead tab pointer and a tab that survives but stops bearing properties
  strand a section identically — no surface renders a property stack on a
  `sections`/`view` tab — so they fall back identically, onto the default
  tab, VISIBLE. Liveness alone missed the re-kind by a two-click path no
  group-editor refusal can cover, because the content kind changes AFTER the
  assignment.
- **`RecordProperties` is deliberately NOT keyed by tab.** Every piece of
  state it owns — the reveal expander, the add-property flyout, a drag in
  flight — is about the RECORD's stack and never read against one tab's
  sections, which re-derive from props every render. A tab-keyed remount
  would discard a flyout the user opened and a reveal they asked for on every
  press and discard no stale state, because there is none. A drag in flight
  cannot be affected either way: `useSortableList` is wired only in the flat
  branch, and `flat` is global.
- **`DocSidePanel` and `InboxPage` pass no tab, on purpose.** InboxPage
  carries no strip, so there is no open tab to scope to and nowhere to go for
  the sections a scope would hide; the side panel stands BESIDE the page
  rather than on one of its tabs. Both now say so in place (846eb99), with
  two DocPage cases that fail if anyone threads a scope through them.
- **The peek renders the stack UNSCOPED when no tab bears properties**
  (89f9734). A type can declare tabs that are ALL Sections or View. The page
  survives that because `DocSidePanel` renders the whole unscoped stack
  whatever tab is open; the peek has no side panel, so the same type left a
  record's groups and loose fields with nowhere at all to render — only the
  heading strip survived, because it sits outside the tab gate. A record's
  properties must be reachable from at least ONE surface, and the peek is the
  only surface a peek user has. The flag short-circuits BOTH halves of the
  gate, because the strip's expander is only offered on an Overview tab and a
  stack folded behind a toggle nothing renders is the same hole one layer
  down.

**Bugs the reviews caught before they shipped:**

- **`seedDraft` would have erased every tab assignment on Apply** (98381fa).
  It rebuilt draft groups as `{id, name, fields}` from the resolved layout,
  and Apply serializes the draft — so opening the customizer on a vault whose
  `layout:` carried `tab:` and pressing Apply UNCHANGED silently dropped every
  one. Fixed by carrying `tab` through `ResolvedLayout`, absent staying
  absent so the deviations-only serializer never learns the key from a
  rebuild.
- **Three position-based index couplings on a filtered canvas** (1d88cf7). A
  render position stopped being a config position the moment the canvas
  filtered by tab, and every id the canvas emits speaks to `moveGroup` /
  `moveField`, which operate on the whole config across every tab. `cfg` is
  addressed by group ID, the bracketing block slots by CONFIG index, the
  trailing one by the config length. Read either off the render index and the
  drop moves the wrong section, or lands a field in another group's slot.
- **"Add section" was reachable where a section cannot land** (b07436c). The
  heading shell renders on every tab, so its editor opens from a `sections`
  or `view` tab — and its footer staged a group ONTO that tab. The engine
  correctly stranded it onto the default tab while `editingValid` unmounted
  the popover: pressed here, landed there, nothing on screen saying so, and
  an unrequested "New group" in the Apply bytes. The footer answers the same
  question the canvas's + does now.
- **The Content block previewed on a `properties` tab** (3b5cdfc), where BOTH
  hosts stand the body down. That is the Overview leaking through on the
  third of the three non-overview kinds — the defect the property zones
  already stand down to stop. The canvas uses DetailPanel's predicate
  verbatim now, not "the tab bears properties".

**Known limitations / honest omissions:**

- **The strip-less-host hole.** `DocSidePanel` mounts `DocProperties`, whose
  non-flat branch renders `headingFolds` only when revealed — so for a
  laid-out type the heading's SHOWN fields render nowhere in that panel.
  Harmless today because `DocPage` co-mounts `HeadingProperties` outside the
  tab-kind gate, so the page always carries them. Filed as an M45.1-era
  defect, not an M45.6 regression; 846eb99 reworded the docblock that claimed
  otherwise (the panel holds sections and the remainder, not "every
  property").
- **The non-identity gap drop** (e45a20c). `handleLayoutDragEnd`'s group
  branch guards a CONFIG identity, and a tab-filtered canvas can part config
  identity from visual identity: with another tab's section occupying the
  config gap drawn just after yours, dropping there commits a REAL reorder
  whose visible result is unchanged on every tab. Nothing the user can see
  moves, the draft goes dirty, and closing asks to discard. Buying the true
  no-op means resolving the preview — the tab roster, the scope, the filter —
  inside a pure handler, to answer a question about a gesture that changes
  nothing. Recorded where the reader meets it instead.
- **Two spellings of one question.** `DocPage`'s stack gate is still the
  hand-written negative pair (`content !== 'sections' && content !== 'view'`)
  while the peek's `propertiesOrphaned` short-circuit asks
  `tabBearsProperties`. Identical today because `TabContent` is a closed
  union of four — the two kinds that are not the pair ARE the two the
  predicate accepts — but they would default OPPOSITE ways if a fifth kind
  were added: the negative pair would show the stack, the predicate would
  hide it. One of them is wrong on that day and neither says which.
- **`editingValid`'s `bearsProperties` arm is defensive only.** Nothing
  reachable can strand the rest editor today: the strip offers no way to
  change a tab's content KIND, so it guards a state only a future affordance
  (or a vault edit under an open dialog) reaches. Kept because rest's shell
  stands down with the group stack, and the alternative to a cheap predicate
  is an anchorless popover over a canvas with no shell under it. 856fdcf
  pinned the arm that IS reachable — a tab REORDER changes which tab is
  default, an untabbed section moves with it, and the selection stands still,
  so nothing calls `setEditing(null)`.
- **Carried, unchanged:** the canvas still does not live-embed a view tab
  (M45.4's weight-without-fidelity ruling; the placeholder follows the active
  tab), and the Simple tile still reseeds `[Overview]` without a confirm.
