# M46.1 — Properties above the tabs Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Reverse M45.6's central model. Property sections are GLOBAL — heading, groups and rest all render above the tab strip, on every tab — and a tab holds only the page body or a data-source view, exactly as Notion does.

**Architecture:** A subtraction, not an addition. `LayoutGroup.tab` and every mechanism built to scope sections by tab retire: the `LayoutTab` argument on `resolveLayout`, `layoutTabScope`, `canHoldSections`, `setGroupTab`, `addGroup`'s tab argument, "Move to tab…", the tab-scoped canvas, and the per-surface tab threading. The `properties` tab kind retires with them. What stays: the peek's tab strip (M45.6 Task 2 — correct and confirmed), the customizer's live tab strip, and view tabs.

**Spec:** `docs/superpowers/specs/2026-08-29-cerebro-m46-notion-parity-polish.md` §2.

## The ruling this implements (user, 2026-08-29)

> "sorry tabs are only for related data sources. fields shwo above. just like notion."

Confirmed against the live Notion app: the property strip renders above the tab strip
and shows on every tab; the tabs hold the page body ("Content") and linked data sources.
A property section never belongs to a tab.

## Decisions this plan locks

- **`LayoutGroup.tab` is deleted from the type, not deprecated.** A vault carrying the
  key — only reachable by someone who ran M45.6 locally, never by a user of a shipped
  build — parses tolerantly, ignores it, and drops it on the next Apply. The parse
  tolerance is the ONLY accommodation; no migration, no compatibility branch.
- **The `properties` tab kind retires.** A tab that shows the property stack is exactly
  what the correction forbids. `TAB_CONTENTS` becomes `overview | sections | view`. A
  vault carrying `content: properties` falls back to `overview` at the parse door, which
  is the existing unrecognised-kind rule — a tab is never dropped, because its id may be
  load-bearing.
- **`overview` means the page body.** With properties hoisted out of the tab, the
  Overview tab is Notion's "Content": the body editor and nothing else.
- **Property surfaces render the full stack above the strip on every tab**, including
  `sections` and `view` tabs. This deletes the M45.6 reachability rules (`DocSidePanel`'s
  exemption comment, the peek's no-property-bearing-tab arm) because the condition they
  guarded against cannot arise: the stack is always on screen.
- **The customizer canvas mirrors that order**: heading → property groups → rest → tab
  strip → the active tab's content. The canvas's tab strip keeps editing tabs; it no
  longer scopes sections, and the `+ Add section` button targets no tab.
- **`rest`, `heading`, and `flat` keep their global semantics** — they were already
  global, and the reason recorded in M45.6 (a per-tab `flat` double-renders a property)
  stands unchanged.

**Decisions:**

- **A retired Properties tab becomes FREE TEXT, not a second body** (0f88358).
  `TAB_CONTENTS` lost `properties`, and the parse door had to send a stored
  `content: properties` somewhere. The obvious landing — the unrecognised-kind
  rule's `overview` — is wrong: `overview` IS the page body, and a type whose
  vault already carried a Properties tab beside its Overview would parse into
  TWO overview tabs, i.e. two body editors on one file, each writing the same
  bytes. `sections` is the honest destination: per-record free text, an empty
  block until someone types in it, and it can stand beside an Overview without
  either one lying about what it edits. The tab is never DROPPED, because its
  id may be load-bearing (a saved selection, a link).
- **`LayoutGroup.tab` is deleted from the type, not deprecated.** A vault
  carrying the key is only reachable by someone who ran M45.6 locally; it
  parses tolerantly, is ignored, and is dropped on the next Apply. That parse
  tolerance is the only accommodation — no migration, no compatibility branch.
- **The M45.6 reachability machinery is GONE because the condition cannot
  arise.** The peek's `propertiesOrphaned` short-circuit, `DocPage`'s
  `tabScope`, `DocSidePanel`'s "surface of last resort" comment and
  `InboxPage`'s "no tab passed, on purpose" paragraph all existed to answer one
  question: where does a record's property stack render when every tab it
  declares refuses to hold one? Under M46.1 the stack is above the strip on
  every tab, so it is always on screen and there is nothing to strand. Deleting
  the guards was mandatory, not optional — a guard against an impossible state
  is a comment that will be believed by the next reader.
- **The heading strip's expander is now offered on every tab.** Its fold is
  the ONE gate left on the stack; gating the toggle by tab kind would strand
  the record's sections behind a strip with no way to open.
- **`RecordProperties` stays keyed by PATH, not by tab** — the M45.6 reason
  survives its model. Every piece of state it owns (reveal expander,
  add-property flyout, a drag in flight) is about the record's stack, and it is
  the same stack on every tab; a tab-keyed remount would discard a flyout the
  user opened and discard no stale state, because there is none.

**The DocPage tab-strip move, and what it costs.** The strip was a `flex-none`
sibling pinned ABOVE the scroll container. There is no way to put properties
above it from there, so it moved into the content column, under the stack.
It scrolls with the record it describes now — which is Notion's order, the
peek's order and the customizer canvas's order — and it costs exactly one
thing, recorded in place at the JSX: **reading an inline diff swaps the whole
canvas out, the strip included, so tabs are unavailable until the diff is
closed.** Accepted deliberately. The alternative is a strip pinned above a
stack it is supposed to sit below, which is the defect this slice exists to
fix. e2e now reaches the strip by scrolling rather than by finding it at a
fixed offset.

**e2e:** the M45.6 journey (`dc67e50`) is reversed rather than trimmed. Its
first claim survives whole — the peek carries the tab strip, M45.6's defect 1,
still fixed and still proven — and its second is replaced by the M46.1 truth:
mint a section in the customizer, put `owner` in it, swap the canvas to Epic's
**view** tab (the exact kind M45.6 said could hold no properties) and watch
only the tail change, then Apply and find the section on both tabs of both
surfaces, above the strip by `compareDocumentPosition` rather than by testid
order, with a Type doc that carries no `tab:` anywhere. Two falsified
assertions elsewhere died with their comments: M45.5's
`order.slice(0,2) === ['heading','tabs']` (the canvas order is
`heading → sections → rest → tabs → content` now — the user's "tabs are on top"
defect is still fixed, the strip just moved further down), and
`view-tabs.spec.ts`'s `page-properties → toHaveCount(0)`, which asserted M45.4's
"the tab IS the content" ruling that this slice reverses. That spec's rescan
trigger no longer hops to Overview to find a property row, because there is one
right there on the view tab — which is the reversal, stated as a journey step.
