# M46.2 — Notion's drag grammar Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Rebuild every drag surface to Notion's measured grammar. The user's words: "drag and drop isnt polsihed etc. like it feels bad to use". The measurement found why — Notion has TWO drag grammars and ours matches neither.

**Architecture:** Two primitives, applied by kind. **List reorder** (property rows, panel rows, tab strips) = transform reflow: the real row follows the cursor, siblings slide, no ghost and no insertion line. **Block reorder** (canvas sections, table rows, board cards) = cloned ghost at 40% + a 4px accent insertion line that is a child of the target. Today `useSortableList` half-implements the first and dnd-kit's slot lines half-implement the second, on the wrong surfaces.

**Reference:** `docs/superpowers/specs/2026-08-29-notion-drag-and-row-reference.md` — every value below is measured from the live app; its "What our implementation would need" section is the acceptance checklist. Dark-theme numbers only; **light-theme equivalents are not measured and must come from our own tokens, never invented.**

---

## Decisions this plan locks

- **Kind decides grammar, not component.** A surface that reorders items WITHIN a list uses C-I; a surface that moves a block among blocks uses C-II. Property rows and panel rows are C-I. Canvas sections, table rows and board cards are C-II. Recorded per call site so the next reader does not have to re-derive it.
- **C-I has no insertion line.** The opened gap IS the indicator. Our current slot-line on property rows is removed, not restyled — this is the single biggest fidelity gap.
- **C-II's line is a child of the target**, `inset-inline: 0`, so it inherits width and indent. A fixed-width list line is what we have and it is wrong for nested or indented targets.
- **The grip replaces the type icon in place** — one `display: grid` cell, `opacity` cross-fade at `0.15s`. **No gutter column.** Our current absolutely-positioned `-left-5` gutter grip changes the row's effective geometry and is the reason rows shift on hover.
- **Press alone changes nothing.** No lift, no shadow, no scale, no cursor change on press. Drag begins on first movement. `grabbing` applies to the dragged subtree, never to `body`.
- **Escape cancels every drag**, restoring order and stripping all drag state. Verify per surface; this is a correctness requirement, not polish.
- **No "Move up"/"Move down" menu items.** Notion has none anywhere; reordering is drag plus a keyboard binding. We already ship them in some menus — they stay for now ONLY where they are the sole keyboard path, and each survivor is recorded with that reason.
- **Keyboard move**: Notion binds `⌘⇧↓` to move-down. The up binding is **not measured** — if we ship `⌘⇧↑` we are choosing it, and the plan says so rather than claiming parity.

## Task 0 findings — this plan AMENDED (2026-08-29)

The baseline (`108dde2`, `docs/superpowers/specs/2026-08-29-cerebro-drag-baseline.md`)
measured 38 of 42 requirements live and corrected two premises of the plan above. The
task list is re-ordered and re-scoped accordingly; the text above stands as written
except where contradicted here.

**A correctness defect outranks all the polish.** `Escape` does not cancel a
`useSortableList` drag, and the measurement is decisive: on the tab strip, after
`Escape` the gesture still tracked the pointer and **the release committed the
reorder**. On the record panel the same keypress closed the panel and left the drag
live. That is data loss by mis-key, not a fidelity gap — it becomes **Task 1**, ahead
of every aesthetic change, and ships with its own test.

**The plan's grip premise was wrong for property rows.** `PropertyRow` already swaps
the grip into the type icon's own 13x13 cell at `absolute inset-0`, and the row
measured 535px both hovered and unhovered — no layout shift. The `-left-5` gutter grip
is real but belongs to the **layout canvas**. Task 2 must NOT "remove the gutter grip
from property rows"; there is none. What survives of Task 2 is unifying **four** grip
primitives (13x13 in-place `PropertyRow`; 16x24 gutter `LayoutCanvas`; 12x16 in-flow
`GroupEditorPopover`; 10x28 leading-edge `ViewTabs`) onto one, and none of the four
shifts layout — so this is consistency work, not a felt-jank fix.

**A third grammar exists and the reference could not have predicted it.** Board cards
translate the real card at 1:1 pointer delta (C-I's mechanism) while ALSO dimming it
to 0.6 with `z-index: 20`, leaving a hole where it was — and the drop target is a
280x2040px whole-column wash carrying no position. It is neither C-I nor C-II and
needs a ruling before it is rebuilt: a card moving between columns is a block move
(C-II), so that is the grammar it should take.

**A fourth drag SYSTEM exists**: `TableView`'s column-header pointer loop, which owns
our only body-level drag hook (`cb-col-dragging` setting `cursor: grabbing !important`
on every element) — the loud inverse of Notion's inline-on-the-dragged-subtree.

**Do not regress a place we are AHEAD.** Our grips are keyboard-operable; Notion's
property rows are not. Parity is the floor, not the ceiling — no task may remove
keyboard reorder in pursuit of a measured Notion value.

**Ranked by felt impact** (the user's complaint is about feel, so this is the build
order after Task 1): nothing follows the cursor in a list reorder -> the canvas
indicator's measured 3px dead band between targets -> **no transitions anywhere**
(every `transition` on every surface computes to `all`, the initial value, where
Notion declares 20ms on hover and 200ms on movement) -> two-to-three hover washes per
row where Notion lights one -> board cards -> grip consistency -> row anatomy numbers
(33 vs 38 pitch, 116 vs 120, 12 vs 14px), felt last.

**Revised task order:** T1 Escape (correctness) · T2 C-I reflow · T3 transitions +
the dead band · T4 C-II ghost and child-of-target line · T5 board cards · T6 grip
unification · T7 row anatomy · T8 re-measure, gate, push.

### The two grammars, and the rule for which surface takes which

**Kind decides, not component.** A surface that reorders items WITHIN a list
takes **C-I**; a surface that moves a block among blocks takes **C-II**.

- **C-I — transform reflow.** `useSortableList`. The press changes nothing;
  the first movement puts `cb-dragging` on the body, freezes the container to
  its measured box and takes every row out of flow; the REAL row follows the
  cursor 1:1 from its grab point, clamped, untransitioned, at `opacity: 1` and
  lifted by `z-index: 1` alone; the neighbours slide over `--motion-move`; the
  gap that opens **is** the indicator — no ghost, no line, zero nodes added.
  Property rows, group-editor rows, option and status rows, the settings
  panel's chains, and both tab strips.
- **C-II — ghost and target-hugging line.** `components/ui/BlockDrag.tsx`. A
  40% clone in a fixed layer at the source's page coordinates, moved by
  `translate3d`; the source stays put at full strength; a 4px line at 43%
  accent, `radius 0`, `z-index 88`, a CHILD of the target with
  `inset-inline: 0`, flipping at the target's midpoint and cross-fading over
  the same 200ms. Canvas field rows and group shells, dashboard widgets, board
  cards.

The rule is the same one that picks a grip: `row` for what a list row carries
in its own leading slot, `block` for what a block carries out in the gutter.

### The defects, which were not polish

The slice was scoped as fidelity work. Most of what it actually repaid was
correctness, and the pattern is worth naming: **a gesture is a claim on global
state, and nothing in the app had been treating it as one.**

1. **Escape committed a reorder instead of cancelling it** (`27b6f8a`).
   Measured on the running app: the key cancelled nothing, the gesture kept
   tracking the pointer, and the RELEASE COMMITTED THE MOVE — while the same
   keystroke closed the record panel behind it. The app has no undo. This is
   why Task 0's baseline reordered the whole plan.
2. **The same class in five more systems** (`5bea81c` `a3dc0b9` `2977d49`
   `4cbd2c3`). The table's column-header drag had no keydown listener at all
   and committed on release, exactly like the reorder. `useTimeDrag` cancelled
   correctly but took the key on window BUBBLE with no `stopPropagation`, so
   one press abandoned the bar AND closed the surface behind it. dnd-kit
   cancels and then lets the keystroke keep going, so one Escape on the canvas
   closed the whole layout editor. And **five resize loops** — the panel edge,
   the column resizer, the dashboard's widget seam and row edge, the pane
   splitter — had no listener either, so Escape reached the surrounding
   surface and the release then wrote the width the user was backing out of.
3. **The stranded `cursor: grabbing !important`** (`5bea81c`). A table
   unmounted mid-drag left `cb-col-dragging` on `<body>` — a grabbing cursor
   on every element in the app, permanently, with no gesture to explain it.
4. **A gantt view writing to disk after unmount** (`a3dc0b9`). `useTimeDrag`
   had no unmount teardown at all, so a view unmounted mid-drag kept its
   window listeners and the release still reached `patchFrontmatter`. A write
   from a surface that is no longer on screen — found by the same audit, not
   named by it.
5. **The layer popped mid-dispatch that still closed the record panel**
   (`44610e7`). dnd-kit runs `onDragCancel` synchronously inside a document
   BUBBLE listener — one phase before window bubble, where `DetailPanel`
   listens. So the panel read an empty layer stack DURING the very Escape the
   drag was cancelling with, and closed. One press, two dismissals: the exact
   case the hook exists to end, reachable anywhere a board or dashboard stands
   beside an open record.
6. **The lost-pointerup layer strand** (`44610e7`). The loops listen for
   `pointermove`/`pointerup`/`pointercancel` and nothing else, so a button
   released outside the window, a tab switch or an OS focus steal left the
   gesture live and its layer on the stack — and `ownsEscape` then answered
   "the drag" for every surface in the app, so **Escape stopped closing
   dialogs, popovers and the panel** until the component unmounted. A NEW
   consequence of the claim: the same scenario used to strand only local
   state.
7. **The freeze frame animated itself in** (`a337782`, Task 8). The C-I freeze
   places every row at the slot it already occupies, but declaring the
   movement transition in that same commit interpolates from the identity, so
   every sibling flew in from the container's origin. Measured: the third row
   of three rendered **56px** above its slot on frame 1 and crawled back over
   eight. Invisible to jsdom, invisible to a screenshot, visible to a frame
   sampler.
8. **The clipped-name tooltip turned itself off** (`436429e`, Task 8).
   `Tooltip` unmounts its child when it stops being disabled, so the state
   that ENABLED the tooltip destroyed the node the measurement was watching;
   the observer went on reporting the detached node's `0/0` and set `clipped`
   back to false for good. Silent on both labels the new 84px name box clips.

### The nine-plus fixtures that could not discriminate

**This is the most reliable defect-finder in the milestone, and the next slice
should budget for it.** Twelve cases across the slice passed equally well on
the broken code and the fixed code. None was wrong about the app; each was
aimed one step to the side of where the behaviour lives. Six recurring shapes:

1. **Asserted at rest, where both branches emit the same bytes.** The board's
   "no column paints a wash" ran with nothing being dragged, where
   `isOver ? wash : tint` and a plain `tint` are identical. Re-aimed to assert
   with a drag in flight and a column actually over.
2. **Asserted before and after, where the defect lives DURING.** The
   `pushLayer`-plus-`ownsEscape` fixtures every Escape surface used read the
   stack on either side of a keystroke. Defect 5 above is what a listener sees
   _inside_ one dispatch, and they passed happily over it. Fixed by asserting
   against a real window-bubble `ownsEscape` listener copied from
   `DetailEscapeLayer`.
3. **A vacuity guard that matched a sentence rather than a thing.** Three
   live-region cases (canvas, dashboard, board) matched the pick-up
   announcement, which a drag with a target from its first frame supersedes in
   the same tick. Re-aimed at the dragged ITEM.
4. **A stub that answered identically for both states the bug is made of.**
   `PropertyRow`'s clipped-name case stubbed `scrollWidth`/`clientWidth` as
   constants, so a detached node measured the same as a live one — and jsdom
   ships no `ResizeObserver`, so the observer branch never ran at all. Defect
   8 is made of exactly those two states. The new case stubs an observer and
   makes the getters honest about `isConnected`.
5. **One case asserting an end state two different sequences reach.** "Slides
   the neighbour on the movement token" was true both before and after defect
   7, because it sampled after the transition had been declared. Split in two:
   the freeze frame says `none`, and the slide arrives after it.
6. **A fixture keyed to an implementation detail rather than to an identity.**
   `ViewTabs.test.tsx` found its container by `[style*="contents"]`. Not
   wrong, but falsified by any fix to the thing it was guarding. It has a
   testid now.

The working method, for the next slice: **break it on purpose.** Task 7 was
verified by moving the wash back to the row (fails 2), restoring the value's
8px radius (fails 2), putting the container gap back to 7px (fails 1) and
setting the strip label at the panel's type (fails 2); Task 8's tooltip case
was checked by restoring the old effect and watching it fail. A case that
cannot be made to fail is not yet a test.
