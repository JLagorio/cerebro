# AppFlowy reference review — 2026-10-26

This continuation completes the feature-family accounting and substantially expands source-body review. AppFlowy's strongest transferable ideas are narrow interaction contracts and recovery cases: stable view identity, explicit editor selection, field-specific controls, observable model readiness, and inspectable transfer progress. Its cloud collaboration, CRDT persistence, team permissions and app-managed models are separate product choices. None is automatically a Cerebro gap or an accepted milestone.

The supplied snapshot is `docs/examples/AppFlowy-main/`. This chapter describes that snapshot, not a deployed product. **F/** below means its `frontend/appflowy_flutter/` directory and **R/** its `frontend/rust-lib/` directory. **Fresh** means a visible source-body read in this continuation; **prior** means evidence retained from the 2026-10-24 audits, explicitly distinguished in the matrix. Neither means executed. No application/reference code, git/index, dependencies, tests, builds, services or providers were changed or run.

## Architecture and execution boundaries

Flutter desktop and mobile surfaces share Bloc/Cubit controllers, protobuf events and Rust listeners. Fresh startup sequencing in [startup.dart:117–157](../../../examples/AppFlowy-main/frontend/appflowy_flutter/lib/startup/startup.dart:117) composes platform handling, window/Rust/plugin/storage/cloud/widget tasks. The plugin “sandbox” is a built-in registry: [sandbox.dart:27–46](../../../examples/AppFlowy-main/frontend/appflowy_flutter/lib/startup/plugin/src/sandbox.dart:27) returns a blank plugin for an absent type and ignores duplicate registration; [runner.dart:1](../../../examples/AppFlowy-main/frontend/appflowy_flutter/lib/startup/plugin/src/runner.dart:1) is an empty class. This is narrowly a registry/runner observation. It does not prove the absence of behavior in the registered plugins, inherited widgets or controllers, and it is not evidence of an extension isolation boundary or marketplace.

The external boundary is substantial. [pubspec.yaml:180–195](../../../examples/AppFlowy-main/frontend/appflowy_flutter/pubspec.yaml:180) pins `appflowy_editor` and editor plugins to external Git revisions. [Cargo.toml:110–159](../../../examples/AppFlowy-main/frontend/rust-lib/Cargo.toml:110) pins AppFlowy-Cloud client crates, AppFlowy-Collab and a LangChain fork. Their core editor algorithms, CRDT internals, cloud authorization and server durability were not fetched or audited. Local wrappers can establish their calls and result handling, not their remote implementation.

Prior traces establish Rust module composition ([module.rs:1–39](../../../examples/AppFlowy-main/frontend/rust-lib/flowy-core/src/module.rs:1)), FFI task/port ingress ([lib.rs:80–185](../../../examples/AppFlowy-main/frontend/rust-lib/dart-ffi/src/lib.rs:80)), local-first collab document construction/opening ([manager.rs:40–350](../../../examples/AppFlowy-main/frontend/rust-lib/flowy-document/src/manager.rs:40)), and the workspace identity check after asynchronous remote construction ([collab_builder.rs:100–160](../../../examples/AppFlowy-main/frontend/rust-lib/collab-integrate/src/collab_builder.rs:100)). The fresh storage/cloud trace below follows a concrete chain: persisted upload row → queue admission → multipart client calls → progress → local completion record. Source contains both useful separation and places where acknowledgement or failure is lost. Do not replace Cerebro's existing typed doors with these mechanics merely because both applications use Rust and SQLite.

## Bounded follow-through

The first useful implementation candidates are AF06–10/18/40–46: a clipboard selection is not deleted before successful admission; failed/partial conversion is visible; a cancelled debounce still has a retained outcome; transfer completion distinguishes staging, provider acceptance and local journal acknowledgement; historical data and repair operate through existing identity-bound owners. These are acceptance improvements, not permission to replace persistence.

The smallest product deltas worth a separate decision are case-sensitive find (AF13), nested/deeper outline (AF15), and portable formula authoring (AF14). Each requires its own source-format and accessibility decision; existing rich/source editing, page templates, database layouts/formulas, IronCalc sheets, comments, outline and conversation sources remain present.

A bounded later acceptance set should exercise: malformed rich clipboard with valid plain fallback; owner switch during file read; two equal basenames with different bytes; unknown image consent; field edit/reload/close; initial shared read failure followed by successful retry; nested popover Escape and IME; stream metadata before subscription; one failed retriever among successes; mid-chunk read failure; remote success with local completion failure; and unavailable migration history. These are proposed cases, not executed tests or a new accepted milestone. Mobile/native screen-reader, live cloud/model, large-dataset performance and all unreviewed leaf paths remain explicit limits.
