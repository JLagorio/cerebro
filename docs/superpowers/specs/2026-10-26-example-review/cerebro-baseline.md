## Interpretation rules for later implementation

1. Compare a complete journey, not two identically named components. “Connect,” “save,” “verified,” “Safe,” “cancelled” and “published” can have very different effects in these repositories.
2. Preserve current owners. React presentation, shared grammar/policy, native authority, durable records and source bytes have distinct jobs; a new screen must consume them rather than mint another authority.
3. Keep the selected workspace separate from the ordinary vault. Portable Markdown bodies do not imply that all metadata lives in frontmatter; a selected SQLite record does not authorize bypassing document recovery.
4. Treat external packages, remote services, paid editions and build gates as boundaries. A wrapper, schema, feature flag or test fixture alone is insufficient delivery proof.
5. Keep no-op, denied, unavailable, pending, cancelled and outcome-unknown distinct. Import/export or retry must disclose what actually happened.
6. Reread affected owners before implementation. Concurrent changes during this review are logged; the dated comparison is not a frozen implementation plan.
