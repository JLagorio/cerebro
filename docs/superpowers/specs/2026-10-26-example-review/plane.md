# Plane reference review — 2026-10-26

Plane is most useful to Cerebro as a reference for explicit planning states, dense work-item interactions, scoped resource binding, and visible asynchronous outcomes. Its hosted team accounts, PostgreSQL authority, object storage and collaboration servers are separate product choices. This review completes the **module-family accounting at the granularity below**, not a semantic read of every source file or a certification of the running product. Recommendations remain candidates, not accepted milestones.

The reviewed local snapshot is `docs/examples/plane-preview/` (the earlier manifest inspection identified version 1.4.2). Source references below abbreviate that prefix as `R/`; `A/` means `R/apps/api/plane/`, `W/` means `R/apps/web/`, `B/` means `R/packages/blocks/src/`, `E/` means `R/packages/editor/src/`, and `L/` means `R/apps/live/src/`. **F** marks fresh numbered body inspection in this pass; **H** marks retained 2026-10-24 evidence, not independently re-proven here. A function body or route declaration is not proof of successful deployment.

## Mechanism traces that change the comparison

**Selection is not the same as mutation availability.** The full selection store and hook retain row identities and range/group state; the selected-row bulk root only advertises an upgrade. Independently, the mounted bulk-delete modal calls a concrete service/route/admin endpoint. Consequently, the earlier shorthand “bulk operations are upgrade-only” must be narrowed to that selected-row toolbar. Conversely, a service's `bulkOperations` call is not proof its community endpoint exists. The freshly traced delete chain returns a count, while Cerebro already retains per-record failure reasons and uses its native batch/trash authority. The strongest adaptation is consistency of selection/focus and error contracts, not adding another bulk subsystem.

**Authenticated intake and anonymous publication split at the base permission.** The board anchor mixin refuses mismatched project identity. Public settings explicitly opt into `AllowAny`; `IntakeIssuePublicViewSet` inherits `IsAuthenticated`. Submission further binds the requested intake to the anchor and sanitizes HTML before creating triage work. Member-side decision mutation validates both serializers before sequential saves; deletion preserves accepted work. The worker normalizes wake behavior but swallows failure into zero. These are concrete admission, mutation and lifetime mechanisms; they do not establish a functioning anonymous external form or crash-atomic workflow. For Cerebro, a local request Type and explicit promotion batch are a bounded candidate; public hosting is not.

**Page collaboration crosses several authorities.** The live authentication handler compares supplied identity with the API's cookie-authenticated user. The project page adapter carries its scope/cookie to the API; the page permission checks active project links, and description save checks lock/archive. The database extension converts between Yjs binary, HTML and JSON, emits fetch/store failures, and force-closes oversize content. The HTML-to-binary first-read migration writes through that API. None of these behaviors implies Cerebro should write merely on opening or replace its ordinary/selected document owners. Failure vocabulary and identity continuity are transferable; CRDT storage and server migration are an architectural decision.

**Background effects need an outcome model beyond a queue.** Export stores progress and rechecks actor access in its worker. Webhook execution validates/pins destination and logs outcomes, but retry is keyed to transport exceptions, a delivery ID is regenerated per invocation, and returned HTTP errors are not automatically raised by the pinned transport. Retention catches batch failures and continues; the generic restore function does nothing. Cerebro can borrow bounded work and visible progress, while preserving reviewed effects, stable identity, typed uncertainty and recoverability. A queue declaration, periodic schedule or log line is not completion or exactly-once proof.

## Acceptance candidates and remaining uncertainty

The highest-value adaptations are bounded extensions to existing owners:

1. **Selection/focus contract:** one active cursor plus a deduplicated selection, explicit group/range behavior, retained failed targets, and scope checks across editing, dialogs, IME, pane parking and rescan. Keep native text selection and row editing usable together.
2. **Async result contract:** stale generations cannot land in another query/account/vault, appended results survive next-page failure, retry preserves the failed cursor, and closing a surface clearly means hide versus cancel. Pending confirmations require visible status and an intentional dismissal rule.
3. **Invalid configuration visibility:** retain invalid saved filter conditions long enough to explain and repair them; never silently broaden a view after schema change. Check shared evaluator/carrier semantics rather than adding a renderer-only interpretation.
4. **Optional planning semantics:** templates and related pages first; explicit sprint commitments, module lifecycle or intake decisions only with a user need, durable identity, one authority and failure/recovery examples. Existing formulas, sheets, views and projects must remain reachable.
5. **Effects/retention acceptance:** distinguish accepted, processing, applied, failed, expired, cancelled and outcome-unknown; separate metadata publication from activation; disclose partial cleanup/export; retain evidence/history required by current references. Current M96 macOS acquisition needs live owned-process/provider/Keychain acceptance rather than another mocked wrapper.

Family coverage is now explicit across the supplied applications, shared packages, auth/API, operational jobs and deployments. It is still not all-lines review: large portions of the 1,364-file web component family, editor extensions, serializers/migrations, public Space role combinations, provider imports, localization payloads, asset pipelines and tests remain structurally cataloged or mechanically screened only. Propel internals are external. No deployed behavior, anonymous-submission flow, performance budget, screen-reader behavior, mobile/native interaction, worker interruption, live credential acquisition, collaboration convergence or backup/restore installation was exercised. Re-read affected current owners before implementing any candidate; this checkout changed during the audit.
