## Current owning seams and why a CLI origin is insufficient

- actions/native_owner.rs: authenticate obtains the real injected main window before locks; RuntimeOwner.classified_transaction owns the retained exact SQLite handle and emits Committed/NotCommitted/CommitUncertain. NativeStoreObservation pins the store descriptor. AuthorityContext::capture_legacy_opening/with_legacy_opening pins the current selected opening.
- Existing NativeActionReadOrigin is installed only on an actual AgentState publication entry and MCP exact-mint slot. It cannot survive a new CLI process as the same live execution authority. mcp::current_native_observation observes the real receipt and RunGrant, but is presently test/native-read-smoke gated. It is useful for an attended composition slice, not a durable workflow identity.
- actions/native_lineage.rs:46 validates a native run against original app_sessions.close_precision=open; it also binds actual runs actor/vault/store/CLI/parent. An old workflow must not evade this by swapping app_session_id or adopting a new CLI subject. Ordinary ACT lineage validation remains unchanged.
- runtime/dispatch.rs:1414 begin_attended is a CLI-oriented row writer; recover_orphaned_attended:1599 closes old running attended rows. A workflow-specific writer and an exact workflow exclusion from that recovery are required; reusing begin_attended alone would silently kill parked workflows after restart.
- actions/native_authority.rs:215 eligible and :560 checked_binding own actual account/grant/current metadata and catalog snapshot checks. Keep them. Native workflow context supplies a proven original subject, not a scope-to-ActionSubject conversion. Existing account grants are keyed to action_native_runs; no production arbitrary-grant writer was found.
- actions/output_handoff.rs:88 register_rows binds the actual current FLOW claim/reservation and invocation. :150 consume_rows owns verified output transfer/ack. Native integration must use these in the existing retained transaction, including cancellation discard.

## Recommended durable identity

Mint one real native operation run for each FLOW run inside authenticated start's known transaction. Use the existing action_native_runs source_kind=attended_operation for the non-CLI owner-authorized operation, with no CLI/parent/client/child identity. A dedicated workflow_run_origins row makes this a workflow operation rather than weakening general attended-operation lineage. Automatic starts later require a separately authenticated, explicit activation grant; they never inherit a template or a current CLI. If root prefers a new source_kind=workflow, that requires a checked shared policy/schema migration rather than merely accepting a new string; the dedicated table is still necessary for reauthorization.

The immutable binding is FLOW run ID → native operation run ID, owner, actor, vault ID, store UUID, original authority ID, workflow/version, creation origin and original configuration/grant identities. Proposed native actor is workflow:<native run id> (fits existing 128-byte identity bound). The native run ID is minted by the owning start writer, not supplied by renderer or recovered from a new source. V43 act_run_id and act_scope_digest use exactly that native operation. Every action's scoped request identity stays fixed for the entire run. No CLI is spawned and no model usage is invented.

Implement runtime::dispatch::begin_workflow_operation_rows as the sole runs writer for this operation: require an existing transaction, native-minted identity and exact scope, use recorded manual/schedule/event cause and actual started time; keep model usage unknown unless measured elsewhere. Choose existing attended mode for a manual start and ambient mode for scheduled/event starts, with workflow rows owning their own finite dispatch reservations; do not insert a fake LLM ambient lease or zero-model success. Exclude exact workflow_run_origins joins from CLI orphan recovery and meter/discard paths; terminal FLOW cleanup finishes its native operation once only. Unknown effects keep both runs nonterminal.

Proposed durable rows, all FK-bound and bounded:

1. workflow_run_origins: workflow_run_id unique, native_run_id unique, immutable owner/vault/store/path/version/authority/configuration/grant identity, authority revision, revoked_at/reason, current admission epoch and current process/session identity. Existing immutable action_native_runs retains creation session facts. A current admission is not a replacement actor/run/ACT scope.
2. workflow_run_action_selectors: (workflow_run_id, step_id), exact action/definition/connection/account plus original catalog snapshot digest captured before start commit. At most 32 rows. V45 copies this original selector identity into a claimed attempt; restart never asks a fresh catalog to choose selectors for a pending step.
3. A bounded original read grant record and explicit account-grant selection metadata associated with the origin, max bounds from shared policy. Requested permissions are data. Only authenticated native Start or explicit Enable reviews and issues them, intersecting the definition's needs with current permitted tools/folders/accounts/capabilities. Missing selection means deny. Account grant rows use existing ACT metadata and revocation rules. No automatic grant from declaredActionDigests, sample input, import or template.

Exact table grouping can share one bounded canonical metadata column if the strict shared schema/digest and byte caps are checked; do not duplicate mapped input or outputs. Authority metadata has an explicit cap distinct from V43 operational values. New limits go into shared/workflows/runtime.v1.json with digest/readers updated, not mirrored constants. Existing activeVaultBytes=268435456, per-step256KiB, output-only per-run8MiB and terminal retention Off remain unchanged.

## Native start and current authorization

New private native_owner::native_workflows owns all producers. Start takes the injected AppHandle/WebviewWindow, selected definition/version, input, persisted idempotency key and explicit requested permission selection. It authenticates the native owner before locks, captures actual current opening and store descriptor, reads the immutable definition through the existing contained files service, and validates all identities. Under opening guard → retained storage → one BEGIN IMMEDIATE it rechecks current runtime readiness, current owner, exact vault/store/session, schema/version, permission selections and capacity; inserts FLOW/native origin/account grants/original selector snapshot together. Returning Existing never mints another origin or changes stored scope. CommitUncertain releases no runnable capsule and retires the owner; recovery looks up the exact existing key.

A private nonserializable WorkflowOrigin contains the original binding and retained native owner/store/opening/session epoch. Its constructor is only authenticated start or authenticated reopen/reconciliation against those durable rows. The public request contains selectors, never a proof. A private borrowed WorkflowMutationContext binds the same Connection, original ACT scope and freshly checked grants for one operation. It implements the existing ACT MutationContext and can be passed only inside the retained owner callback. No general ActionSubject factory, Connection accessor or arbitrary writer callback is exposed beyond native_owner descendants.

For read, the native owner creates an actual constrained RunGrant only from its verified workflow grant record/current-policy intersection and original native run. This is a production grant issuer analogous to existing native run minting, not a constructor from StepWork/Scope. Keep scope write-denied, tools limited to the real query tool, exact stored vault, explicit read scope and unattended mail semantics; a workflow is never an attended chat merely because manual start used a window. The grant remains borrow-only inside the guarded read adapter. Existing workflows::read::execute then reuses the real corpus/filter/query path. Read admission rechecks exact origin epoch/tool/vault immediately before I/O and original claim CAS before settlement; stale read results cannot advance.

## Restart, waits and revocation

On desktop startup/opening, no old in-memory capsule is restored. A bounded reconciliation batch SELECTs candidate workflow rows for the exact currently ready vault/store, prioritizing cancellation and existing ACT observation before new work. It authenticates the current native desktop owner/opening and issues a fresh admission epoch to the SAME immutable workflow/native/ACT subject only after original permissions remain valid under current policy/account grants. It never updates immutable identity or frozen request snapshots. A changed account/catalog snapshot blocks old work for explicit review; it does not rewrite request digest. Reauthorization narrows capability; it cannot grant something outside the run's original selection. Explicit broader grants require a separately reviewed operation/new run.

Current session/opening are checked through the new workflow-origin admission row. Do not relax native_lineage::validate_row for general old native runs. The workflow-specific context checks creation row consistency, exact original workflow binding, current admission session readiness, revocation revision and original permission intersection. Generic ACT root/client/CLI paths keep their existing liveness rules.

Each process keeps a bounded retained workflow worker book; epoch/CAS plus a nonblocking physical per-workflow lease prevent two desktop processes executing the same read/local step. Reuse the reviewed physical lease ownership machinery, with workflow namespace binding and identity checks; do not use a timeout as proof a worker finished. One active step per run; sequential cursor remains authoritative. If a read is known claimed but lacks a durable result after an actual process restart, mark interrupted/block for explicit retry rather than silently rereading to render history. Read-only retry can be an explicit new reviewed attempt policy later; current V43 one-attempt semantics remain honest.

Waits and unknown effects have no TTL-based terminalization or content reclamation. Existing due/expiry bounds apply. A timer can advance only while desktop runtime/current workflow authority are ready; overdue stays waiting with lateness, no replay storm. Pause/unpublish stops new automatic starts, not existing runs; global readiness/recovery can defer execution without cancellation. External input must authenticate the local native person or a real separately issued inbound capability and existing continuation; person approval goes through ACT's actual owner decision, never a run bearer. Unknown/missing output only reconciles original invocation and V44 receipt. It never prepares a new attempt or converts known success to unknown.

Bounded reconciliation needs shared policy fields for maximum runs per batch, workers and interval; propose 32 candidate rows per pass, 1 worker, 1 second minimum interval with wake hints coalesced. Root approved these execution bounds on 2026-10-26. No new schedule starts until activation service and explicit Enable are implemented; no catch-up/retention choice is inferred.

## One-transaction ACT handoff and retained settlement

The M96 action bridge proposes with_attended_mutation(app,window,run, callback(&Connection,&dyn MutationContext,&ActionSubjectView)) for the original attended integration tests. The workflow-origin sibling uses the same kernel callback shape with its own real producer and current checks. In the transaction: apply current FLOW claim/V45 freeze, ACT prepare using the frozen selectors, register V44 consumer, observe canonical ACT state, and park/advance once. A domain error rolls all rows back; commit uncertainty returns no worker. Known committed ACT claim alone mints the M96 action bridge's Submission capsule. StepWork and frozen selector records remain data.

the M96 action bridge's current Submission stores Arc<NativeActionReadOrigin>; factoring the private origin carrier into an enum of real Attended and Workflow producers is needed. Both provide exact original runtime seal/store/native scope fingerprints and cancellation registration. Dispatch revalidates current origin/grants before HTTP first poll. Settlement uses the original retained capsule and actual invocation/attempt, even if the originating opening/grant is now retired; it can record observation/receipt only, never start work. Provider runtime cleanup and physical lease finish before capsule release. FLOW output consume/ack can occur in that settlement transaction or the next bounded authenticated reconciliation; receipt remains protected until then. Terminal cancellation must discard/ack in the same transaction that releases FLOW values/reservation.
